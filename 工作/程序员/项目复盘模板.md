# 程序员 · 项目复盘模板（STAR / 技术选型 / 踩坑 / 指标）

> 把「做过」变成「能讲、能写、能加分」的项目资产。本文给完整模板 + 可抄改的示例，既用于简历，也用于面试深挖和团队复盘。

## 一、STAR 结构模板（项目描述的骨架）

```
- **S（背景 Situation）**：项目服务谁、解决什么问题、规模多大。
- **T（任务 Task）**：你的角色、职责边界、独立负责的部分。
- **A（行动 Action）**：具体方案、技术选型、关键决策及理由。
- **R（结果 Result）**：量化指标、影响、你的独特贡献。
```

- 四段缺一不可；面试讲项目按 S→T→A→R 顺序，每段 30–60 秒。
- 常见错误：S、T 过长（面试官想听的是 A 和 R）；A 报菜名（只列中间件）不给理由；R 没有数字。

## 二、技术选型复盘（面试官最爱追问的「为什么」）

| 决策点 | 复盘问题 | 示例回答框架 |
| --- | --- | --- |
| 为什么用这个中间件 | 当时的备选有哪些？对比过什么指标？ | 备选 Redis vs Memcached，因需要持久化 + 数据结构丰富选了 Redis |
| 为什么用这个框架/语言 | 团队基础、生态、学习成本怎么权衡 | 团队 Java 基础好、Spring 生态全，选 Spring Boot 而非 Go |
| 数据量/QPS 依据 | 预估基于什么？上线后验证了吗 | 按订单峰值预估约 2 万 QPS，压测验证后留了 30% 余量 |
| 如果重来 | 现在知道什么？哪里会改 | 会用 Kafka 替代自研队列，因为积压排查成本高 |

- 复盘句式：**「当初为什么选 X → 遇到过什么坑 → 如果重来怎么选」**，一段话讲清，比背框架强。

## 三、踩坑记录（复盘的精华区）

- 按「现象 → 定位 → 根因 → 修复 → 预防」五步写：
  - 现象：什么时间、什么表现（报错、告警、用户反馈）。
  - 定位：怎么排查的（看日志、加监控、复现路径）。
  - 根因：最底层的原因（代码、配置、依赖、容量）。
  - 修复：改动是什么、怎么验证的。
  - 预防：加了什么监控/测试/规范，避免再犯。
- 高频踩坑类型自查：
  - 缓存穿透/击穿/雪崩、分布式锁过期、消息重复消费、慢 SQL、内存泄漏、时区/编码问题。
- 面试讲踩坑 = 高光时刻：选一个「你主导定位 + 你主导修复」的，讲出排查路径，比讲成功项目更能证明水平。

## 四、指标复盘（让结果可量化）

- 通用技术指标：QPS/并发量、延迟（P50/P95/P99）、可用性（SLA）、资源成本（CPU/内存/带宽）、发布效率。
- 业务指标：转化率、留存、客诉量、GMV 占比、人效。
- 没有线上指标时：压测数据（标注压测条件）、代码规模（模块数/接口数）、流程提升（发布从 2 小时到 10 分钟）。
- 数字来源标注：真实数据 / 压测数据 / 估算——避免面试被追问时露馅。

## 五、完整模板 + 示例（可直接抄改）

### 5.1 简历版（2–3 行，配数字）
```
会员积分系统（S：平台约 50 万注册用户）
独立完成积分计算、发放与防刷（T）
采用 Redis 预扣 + 幂等表防重复发放，本地消息表保证最终一致（A）
上线后月活渗透率 60%，客服积分类工单降约 70%（R）
```

### 5.2 面试深挖版（1–2 分钟讲述结构）
- S（10 秒）：一句话背景 + 你在哪一环。
- T（15 秒）：你的职责与难点。
- A（60 秒）：方案 + 为什么 + 权衡，重点讲「当时的取舍」。
- R（15 秒）：数字结果 + 你的独特贡献 + 「如果重来会改哪里」。

### 5.3 团队复盘会版（事故/迭代后用）
```
1. 目标与结果：本次迭代的目标是什么、达成率多少。
2. 做得好的：值得固化的 2–3 点（流程/技术/协作）。
3. 问题与踩坑：现象/根因/修复/预防（用第三节五步法）。
4. 数据对比：关键指标 vs 上一周期。
5. 下一步行动：具体责任人 + 截止时间 + 验证方式。
```

### 5.4 面试讲述示例（完整话术骨架）
```
「这个项目是 XX 系统的核心模块，我负责 XXX（S/T）。
当时难点是 XX 场景下的 XX 问题（如并发扣减不重不漏），
我对比了 A/B 两种方案，选了 X，因为……（A 的取舍）。
上线后 XX 指标从 X 降到 Y，用户反馈 XX（R）。
如果重做，我会提前把 XX 的监控加上——这是当时踩过的坑。」
```

- 持续积累：每个项目维护一份「项目档案」（背景/决策/踩坑/指标各一页），面试季直接提取，不用临时回忆。

> 一句话：**没有复盘的项目等于没做；有复盘模板的人，面试就是讲故事。**

## 六、复盘方法论：三种经典框架

### 6.1 GRAI 复盘法（联想/阿里常用）

| 步骤 | 含义 | 关键问题 |
| --- | --- | --- |
| **G（Goal）目标** | 当初要做什么 | 目标是否清晰、可量化？ |
| **R（Result）结果** | 实际做到了什么 | 与目标的差距是多少？ |
| **A（Analysis）分析** | 为什么产生差距 | 做得好/不好的根本原因是什么？ |
| **I（Insight）洞察** | 学到了什么 | 哪些经验可以固化？哪些要改？ |

- 适用场景：项目结束后、季度/年度总结、重大事故复盘。
- 输出物：一页纸的 GRAI 复盘表，团队全员参与填写。

### 6.2 KPT 复盘法（敏捷/快速迭代场景）

| 步骤 | 含义 | 示例 |
| --- | --- | --- |
| **K（Keep）保持** | 做得好且要继续保持的 | 每日站会同步进度、自动化测试覆盖率 80%+ |
| **P（Problem）问题** | 遇到的问题和困难 | 联调环境不稳定导致返工 3 次 |
| **T（Try）尝试** | 下一步尝试改进的 | 引入 Docker Compose 统一本地开发环境 |

- 适用场景：迭代回顾会、每周复盘、日常改进。
- 输出物：便利贴白板（线下）或飞书文档表格（线上），每项有 owner 和截止时间。

### 6.3 AAR 复盘法（美军/项目管理经典）

| 步骤 | 含义 | 核心问题 |
| --- | --- | --- |
| **1. 预期目标** | 我们打算做什么 | 目标是什么？衡量标准是什么？ |
| **2. 实际发生了什么** | 按时间线还原事实 | 关键事件节点、决策点、结果 |
| **3. 为什么不同** | 分析差距原因 | 哪些假设错了？哪些信息缺失？ |
| **4. 下次怎么做** | 改进行动 | 具体措施、责任人、验证方式 |

- 适用场景：重大事故、跨部门协作、复杂项目复盘。
- 特点：强调「按时间线还原事实」，适合事后分析而非实时改进。

> 来源：《复盘：对过去的事情做思维演练》、联想内部复盘方法论、美军 AAR 手册

## 七、复盘会议组织实操

### 7.1 会前准备（决定复盘质量的 80%）

| 准备项 | 具体做法 |
| --- | --- |
| **确定范围** | 明确复盘什么：整个项目、某个模块、某次事故？范围太大会空泛 |
| **收集数据** | 项目时间线、关键决策记录、线上指标、代码变更记录、工单数据 |
| **邀请参会人** | 全员参与（开发/测试/产品/运维），至少参与过核心环节的人 |
| **预设问题** | 提前发 3–5 个引导性问题让大家准备，避免开会时无话可说 |
| **指定记录人** | 安排人记录讨论内容和 action item，会后整理成文档 |

### 7.2 会中引导（避免复盘变成甩锅会）

- **开场定调**：「今天不是追责，是找改进点」——先声明复盘目的。
- **时间线还原**：先按时间线把事情过一遍，对齐事实再分析原因。
- **先找做得好的**：不要上来就批评，先肯定做得好的 2–3 点，建立安全感。
- **分析根因**：用「5 个为什么」追问根因，不要停在表面原因。
- **产出 Action Item**：每个改进点要有 owner + 截止时间 + 验证方式。
- **控制时间**：60–90 分钟为宜，超过 2 小时效率急剧下降。

### 7.3 会后跟进（没有跟进的复盘等于没开）

- 24 小时内发出会议纪要（含 action item 列表）。
- 每周/双周检查 action item 进展。
- 下次复盘开头先回顾上次的改进措施执行情况。

> 来源：《The Retrospective Handbook》、ThoughtWorks 复盘实践

## 八、常见问题分析工具

### 8.1 五个为什么（5 Whys）

```
问题：线上服务响应变慢
→ 为什么？数据库查询变慢
→ 为什么？慢 SQL 增多
→ 为什么？新上线的接口没加索引
→ 为什么？代码 Review 没发现
→ 为什么？Review 只关注逻辑不关注性能
→ 根因：缺少性能 Review checklist
```

- 追问 3–5 层通常能找到根因；追问到「流程/制度」层面才是真正的改进点。

### 8.2 鱼骨图（因果分析）

| 类别 | 可能原因 |
| --- | --- |
| **人员** | 新人经验不足、分工不明确 |
| **流程** | 需求评审走过场、Code Review 不严格 |
| **技术** | 架构设计缺陷、监控覆盖不足 |
| **工具** | 测试环境不稳定、部署流程手动 |
| **外部** | 第三方服务不稳定、需求频繁变更 |

### 8.3 常见技术问题分类与改进方向

| 问题类型 | 高频场景 | 改进方向 |
| --- | --- | --- |
| **性能问题** | 慢 SQL、缓存失效、内存泄漏 | 性能 Review + 监控告警 + 压测 |
| **稳定性问题** | 服务雪崩、单点故障、级联失败 | 限流降级 + 多活部署 + 混沌工程 |
| **安全问题** | SQL 注入、XSS、权限绕过 | 安全扫描 + 渗透测试 + 权限最小化 |
| **协作问题** | 需求理解偏差、联调困难 | 需求文档化 + 接口契约 + Mock |
| **效率问题** | 发布慢、环境不一致、手动操作多 | CI/CD 自动化 + Docker 统一环境 |

> 来源：《丰田生产方式》、《持续改进》、ThoughtWorks 技术雷达

## 九、如何写好复盘报告

### 9.1 复盘报告结构模板

```markdown
# 项目复盘报告

## 一、基本信息
- 项目名称 / 时间范围 / 参与人员

## 二、目标与结果对比
| 指标 | 目标值 | 实际值 | 达成率 |
| --- | --- | --- | --- |

## 三、时间线还原
- 按关键节点列出：做了什么决策、产生了什么结果

## 四、做得好的（Keep）
1. ...
2. ...

## 五、做得不好的（Problem）
1. 现象 → 根因分析（用 5 Whys）
2. ...

## 六、改进行动（Try/Action）
| 改进项 | Owner | 截止时间 | 验证方式 |
| --- | --- | --- | --- |

## 七、经验沉淀
- 哪些可以固化到团队流程/规范中？
```

### 9.2 写复盘报告的三个原则

| 原则 | 做法 | 反面 |
| --- | --- | --- |
| **用数据说话** | 每个结论配数据支撑 | 「感觉做得还行」 |
| **对事不对人** | 分析流程和系统问题 | 「XX 搞砸了」 |
| **可执行** | action item 具体可验证 | 「下次注意」 |

- 好的复盘报告 = **事实 + 分析 + 行动**，缺任何一个都只是形式主义。
- 写完后给相关人 review，确保分析和改进方向得到认同。

## 十、建立团队复盘文化

### 10.1 为什么复盘文化难以建立

| 障碍 | 表现 | 破解方法 |
| --- | --- | --- |
| **怕追责** | 大家不愿意暴露问题 | leader 先承认自己的错误，定「不追责」基调 |
| **没时间** | 赶进度来不及复盘 | 复盘本身就是工作的一部分，不是额外负担 |
| **形式主义** | 复盘变成走过场 | 有数据、有 action item、有跟进，才算复盘 |
| **没闭环** | 复盘完不执行改进 | 每周检查 action item，纳入绩效考核 |

### 10.2 让复盘持续运转的机制

1. **固定节奏**：每个迭代/月度/季度固定复盘，形成习惯。
2. **轮值主持**：每次复盘由不同人主持，降低 leader 独自推动的压力。
3. **知识沉淀**：复盘结论归档到团队知识库（Confluence/飞书文档），新人入职必读。
4. **改进追踪**：用看板/表格追踪 action item，未完成项在下次复盘开头回顾。
5. **正向激励**：公开表扬提出好改进点的人，鼓励暴露问题而非隐藏问题。

### 10.3 复盘的终极目标

- **不是为了写报告**，而是为了让团队下一次做得更好。
- **不是为了证明谁对谁错**，而是为了让系统和流程更健壮。
- **不是一次性的动作**，而是一种持续改进的思维方式。

> 一句话：**复盘的本质是学习。最好的团队不是不犯错的团队，而是犯过的错只犯一次的团队。**
