# 云计算与大数据

> 子类：计算机与AI ｜ 难度：成人通识 ｜ 阅读时长：约 30 分钟

## 导语

二十年前，一家公司要上线一个网站，得先买服务器、租机房、拉专线、配空调、请运维；今天，同一个人打开浏览器点几下，十分钟内就能拿到一台在异地数据中心的机器，按小时付费，用完就关。

这笔账背后的转变叫**云计算**：把算力、存储、网络变成像水电一样按需取用的服务。而当数据量从 GB 涨到 PB，单机再也装不下时，另一条技术线登场——**大数据**：用成千上万台普通机器协作，把"装不下、算不完"变成"分而治之"。

本篇把这两条线讲清楚：先按 NIST 的权威定义认识云的五特征、三模型、四部署；再向下看支撑云的两块技术地基——**虚拟化**与**容器**；然后进入分布式世界，讲清 CAP 定理的取舍、MapReduce 的"移动计算而非移动数据"、从数据仓库到数据湖再到湖仓一体的演进；最后是边缘计算、Serverless 与云成本。

技术事实均标注来源（如 `NIST SP 800-145`、`CNCF`、`OCI`、`Dean & Ghemawat, 2004`）。

## 第一章 云计算是什么

### 1.1 权威定义

美国国家标准与技术研究院（NIST）在 **SP 800-145** 中给出云计算的定义：

> 云计算是一种模型，它能够实现对**可配置计算资源**（如网络、服务器、存储、应用和服务）共享池的**泛在、便捷、按需**的网络访问，这些资源可以**快速供给和释放**，且只需最少的管理工作或服务提供商交互。

这个定义由三部分组成：**五个基本特征、三种服务模型、四种部署模型**，共 14 个相互关联的术语。

> 来源：NIST, *SP 800-145: The NIST Definition of Cloud Computing*（最终版 2011 年 9 月；其草案自 2010 年起在业界广泛流传）。该定义后来也被 ISO/IEC 17788 与 ITU-T Y.3500 采纳为国际标准的核心概念。

### 1.2 五个基本特征

| 特征 | 英文 | 含义 |
|------|------|------|
| 按需自助服务 | On-demand self-service | 用户可自行开通算力、存储，无需人工介入 |
| 泛在网络访问 | Broad network access | 通过网络访问，支持手机、笔记本等各类终端 |
| 资源池化 | Resource pooling | 多租户共享资源池，按需动态分配，用户通常不知资源确切位置 |
| 快速弹性 | Rapid elasticity | 可快速扩容与缩容，对用户"看起来容量无限" |
| 可计量服务 | Measured service | 自动计量与监控资源使用，按用量计费 |

**"快速弹性"是云与传统托管最本质的区别**：传统方案扩一台机器要等采购与上架；云上扩一百台可能只需要改一个数字。

### 1.3 三种服务模型

| 模型 | 全称 | 用户管什么 | 类比 |
|------|------|------------|------|
| IaaS | Infrastructure as a Service | 操作系统、运行时、应用、数据 | 租一块地，自己盖房 |
| PaaS | Platform as a Service | 只需管应用与数据 | 租一套装修好的公寓 |
| SaaS | Software as a Service | 只管用 | 住酒店 |

NIST 原文的界定（简化）：

- **IaaS**：提供处理、存储、网络等基础计算资源，用户可部署任意软件（含操作系统与应用）；用户不管理底层基础设施，但可控制操作系统、存储、已部署应用，并可能对部分网络组件（如主机防火墙）有有限控制。
- **PaaS**：提供受支持的语言与工具，让用户部署自建或采购的应用；用户不管理网络、服务器、操作系统、存储，但可控制已部署应用及可能的托管环境配置。
- **SaaS**：用户使用运行在云基础设施上的提供方应用，通过浏览器等瘦客户端访问；用户不管理底层设施，甚至不管理单个应用能力（除有限的用户个性化配置）。

### 1.4 四种部署模型

| 模型 | 范围 | 典型场景 |
|------|------|----------|
| 公有云 | 面向公众开放 | 大多数创业公司与互联网业务 |
| 私有云 | 仅供单一组织使用 | 金融、政务、涉密 |
| 社区云 | 若干有共同诉求的组织共享 | 行业云、区域医疗云 |
| 混合云 | 两种以上云的组合，保持独立但可互通 | 核心数据本地 + 弹性业务上云 |

**"混合云"为什么流行？** 因为它同时解决两个诉求：敏感数据放在自己可控的环境，业务高峰时借用公有云的弹性。

### 1.5 云的历史脉络

| 时期 | 关键进展 |
|------|----------|
| 1960s | 分时系统与"计算像水电一样"的设想 |
| 1990s | 虚拟化技术成熟，为资源切分提供基础 |
| 2000s 中期 | 公有云服务商出现，IaaS 走向商用 |
| 2011 年 | NIST 发布 SP 800-145，给出云计算的权威定义 |
| 2013—2015 | 容器（Docker）与容器编排（Kubernetes）兴起 |
| 2015 年至今 | 云原生、Serverless、边缘计算与云边协同 |

## 第二章 三种服务模型详解与责任边界

### 2.1 你到底要管到什么程度

这是选型时最该问的问题。**云不是"把运维外包"**，而是"把运维分层，各自承担一块"。

| 层次 | 自建机房 | IaaS | PaaS | SaaS |
|------|----------|------|------|------|
| 应用 | 你 | 你 | 你 | 厂商 |
| 数据 | 你 | 你 | 你 | 厂商（你拥有内容） |
| 运行时/中间件 | 你 | 你 | 厂商 | 厂商 |
| 操作系统 | 你 | 你 | 厂商 | 厂商 |
| 虚拟化 | 你 | 厂商 | 厂商 | 厂商 |
| 服务器/存储/网络 | 你 | 厂商 | 厂商 | 厂商 |
| 机房/电力/制冷 | 你 | 厂商 | 厂商 | 厂商 |

**责任共担模型（Shared Responsibility Model）** 的要点是：**厂商负责"云本身的安全"，你负责"云里面的安全"**。无论哪一层，数据与访问权限始终是你的责任——这是很多安全事件的根本误解来源（参见《数据安全与隐私保护》）。

### 2.2 何时选哪种

| 需求 | 建议 | 理由 |
|------|------|------|
| 想要最大控制权、需自定义内核/网络 | IaaS | 可自由配置 |
| 专注写业务代码、不想管服务器 | PaaS | 平台承担运维 |
| 直接用成熟软件（邮箱、办公套件、CRM） | SaaS | 零运维 |
| 数据库、消息队列等托管服务 | 托管 PaaS（常称"某某 as a Service"） | 用托管换省心 |
| 极端成本敏感且负载稳定 | 自建或预留实例 | 长期看可能更便宜 |

**一条务实原则**：**差异化能力自己做，通用能力用托管**。没有哪家公司因为自建邮件系统而赢得竞争。

### 2.3 "云"不等于"虚拟机的集合"

云的判定标准是那**五个基本特征**，而不是"是否用了虚拟机"。一个内部机房上了虚拟化，但需要人工审批、按年付费、无法自助扩容的，严格按 NIST 定义并不算云。

> 一个有趣的细节：NIST 在后续分析文档中指出，任何能力要被称为"某某即服务（aaS）"，**必须同时满足云的五个基本特征**。

## 第三章 虚拟化：云的技术地基之一

### 3.1 为什么需要虚拟化

物理服务器常常利用率很低——一台机器可能只跑了一个应用、CPU 长期闲着。虚拟化把一台物理机切成多个相互隔离的虚拟机，让资源被充分利用，同时提供隔离与快速复制。

| 收益 | 说明 |
|------|------|
| 提高利用率 | 一台物理机跑多个负载 |
| 隔离 | 一个虚拟机崩溃不拖垮邻居 |
| 快速部署 | 虚拟机镜像一键复制 |
| 灵活迁移 | 可在不停机的情况下迁移到别的物理机 |
| 快照与回滚 | 出问题可回退到某个时间点 |

### 3.2 虚拟机监控器（Hypervisor）

**Hypervisor** 是负责创建与运行虚拟机的软件层，分两类：

| 类型 | 说明 | 特点 |
|------|------|------|
| Type 1（裸金属） | 直接运行在硬件上 | 性能好、安全性高，数据中心主流 |
| Type 2（宿主型） | 运行在操作系统之上 | 便于个人使用，性能有损失 |

### 3.3 虚拟化方式对比

| 方式 | 原理 | 性能 | 兼容性 |
|------|------|------|--------|
| 全虚拟化 | 客户机指令全部由 Hypervisor 模拟/翻译 | 较低 | 最好，无需改操作系统 |
| 半虚拟化 | 客户机内核需做改造，主动配合 | 较高 | 需支持改造的系统 |
| 硬件辅助虚拟化 | CPU 提供虚拟化指令直接支持 | 高 | 需 CPU 支持（现代 CPU 普遍具备） |

### 3.4 虚拟机的代价

虚拟机虽好，但**每个虚拟机都要带一整套操作系统**：

| 项目 | 虚拟机 | 容器 |
|------|--------|------|
| 启动时间 | 分钟级 | 秒级甚至更快 |
| 体积 | GB 级 | MB 级 |
| 操作系统 | 每个实例一套 | 共享宿主内核 |
| 隔离强度 | 强（硬件级隔离） | 较弱（内核级隔离） |
| 密度 | 一台机器几十个 | 一台机器可上百个 |

**"启动慢、太重"正是容器要解决的问题。**

### 3.5 云主机与"弹性"的关系

云厂商提供的"云服务器"本质是虚拟机：用户按规格选择 CPU/内存/磁盘，几分钟内创建完成，可随时释放、调整规格、做镜像与快照。**"快速供给与释放"这一 NIST 特征，正是靠虚拟化实现的。**

## 第四章 容器与编排：更轻的隔离单元

### 4.1 容器是什么

**容器（Container）** 把应用及其依赖打包成一个可移植的单元，**共享宿主操作系统内核**，只隔离进程、文件系统、网络等视图。

它依赖 Linux 的两项核心机制：

| 机制 | 作用 |
|------|------|
| 命名空间（namespace） | 隔离"看得见什么"：进程号、网络、挂载点、主机名等 |
| 控制组（cgroup） | 限制"能用多少"：CPU、内存、I/O 配额 |

**一句话区分**：虚拟机虚拟的是**硬件**，容器虚拟的是**操作系统**。

### 4.2 容器技术的演进

| 时间 | 事件 |
|------|------|
| 2013 年 | Docker 发布，极大降低了容器的使用门槛 |
| 2014 年 | Kubernetes 由 Google 开源，源自其内部系统 Borg |
| 2015 年 | Open Container Initiative（OCI）成立，制定镜像与运行时标准 |
| 2015 年 | Cloud Native Computing Foundation（CNCF）成立，Kubernetes 捐赠给 CNCF |
| 2017 年 | Docker 将 containerd 捐赠给 CNCF |
| 2020 年 | Kubernetes 宣布弃用 Dockershim，转向符合 CRI 的运行时 |

> 来源：OCI 由 Linux 基金会于 2015 年发起，产出 **OCI 镜像规范**与**运行时规范**两项标准；Kubernetes 由 Google 于 2014 年开源，2015 年捐赠给 CNCF；containerd 于 2017 年捐给 CNCF。Kubernetes 官方在 2020 年的发布说明中宣布弃用 Dockershim。

**为什么 Docker 之后还要标准化？** 因为各家实现不互通会导致厂商锁定。OCI 规范让"镜像格式"与"运行时接口"统一，于是 Docker、CRI-O、containerd 等都能运行符合 OCI 标准的镜像。

### 4.3 容器编排：Kubernetes 做什么

当容器从几个变成几千个，手工管理完全不可行。**编排系统**承担：

| 能力 | 说明 |
|------|------|
| 调度 | 决定容器放在哪台机器上 |
| 自愈 | 容器挂了自动重启，节点故障自动迁移 |
| 扩缩容 | 按 CPU/内存或自定义指标自动增减副本 |
| 服务发现与负载均衡 | 自动分配访问入口并分发流量 |
| 滚动更新与回滚 | 平滑升级，出问题快速退回 |
| 配置与密钥管理 | 把配置从镜像中分离 |
| 存储编排 | 为有状态服务挂载持久卷 |

**"声明式"是 Kubernetes 的核心设计**：你描述"期望状态"（要 3 个副本），系统负责把现实拉回期望。这与传统"执行一串命令"的命令式方式形成鲜明对比。

### 4.4 无状态与有状态

| 类型 | 特点 | 在容器里 |
|------|------|----------|
| 无状态服务 | 不保存会话数据，可随意替换 | 天然适合容器，扩缩容简单 |
| 有状态服务 | 需要持久化数据（数据库等） | 需要持久卷、有序启动、专用 Operator |

**这是容器化改造中最难的部分**：把有状态系统（数据库、消息队列）容器化，需要额外的数据持久化与一致性保障。

### 4.5 云原生

**云原生（Cloud Native）** 不只是一组工具，而是一种构建与运行应用的方式：容器化、动态编排、微服务、声明式 API、持续交付、可观测性。

> CNCF 对云原生的定义为（意译）：一种使组织能够在公有云、私有云和混合云等动态环境中，构建和运行**可弹性伸缩**应用的技术方法；容器、服务网格、微服务、不可变基础设施和声明式 API 是其典型技术。

## 第五章 云存储：三种形态

### 5.1 对象、块、文件

| 类型 | 访问方式 | 特点 | 典型用途 |
|------|----------|------|----------|
| 对象存储 | HTTP API，以"对象 + 元数据"为单位 | 近乎无限扩展、便宜、最终一致；不适合频繁改单字节 | 图片、视频、备份、静态网站 |
| 块存储 | 挂载为一块"云硬盘" | 低延迟、可随机读写 | 数据库、虚拟机系统盘 |
| 文件存储 | 网络文件系统协议 | 多机共享同一目录树 | 共享配置、容器共享卷、HPC |

**它们的差别可以这样记**：

- 对象存储像**快递仓库**：存进去时贴个单号（键），取出时凭单号一次拿整件；
- 块存储像**一块可擦写的硬盘**：可以任意位置读写；
- 文件存储像**共享网盘**：多台机器看到同一套目录。

### 5.2 冗余与可靠性

云存储用**多副本**或**纠删码**保证数据不丢：

| 方式 | 原理 | 代价 |
|------|------|------|
| 多副本 | 存 3 份（常见） | 空间开销 3 倍 |
| 纠删码 | 把数据切成 n 块并生成 m 块校验 | 空间开销更低，但重建需要读取更多块 |

**可靠性指标（"几个 9"）**：

| 可用性 | 年累计不可用时间（约） |
|--------|------------------------|
| 99% | 约 3.65 天 |
| 99.9% | 约 8.8 小时 |
| 99.99% | 约 53 分钟 |
| 99.999% | 约 5 分钟 |
| 99.9999% | 约 32 秒 |

**注意区分"可用性"与"持久性"**：云存储常宣传"持久性 11 个 9"，那是"数据不丢的概率"，不是"随时能访问的概率"。

### 5.3 一致性模型

分布式存储里，"你刚写的数据，别人多久能读到"是个必须明确的问题：

| 模型 | 保证 |
|------|------|
| 强一致 | 写成功后任何读都能看到最新值 |
| 最终一致 | 一段时间后所有副本趋于一致，期间可能读到旧值 |
| 读己之写 | 至少自己写的自己一定读得到 |

**为什么会不一致？** 因为副本复制需要时间，网络会延迟、会分区——这直接引出了下一章的 CAP 定理。

### 5.4 分层存储与生命周期

云存储通常提供"热/温/冷/归档"多档位，价格依次降低、取回时间依次变长。通过**生命周期规则**自动把老数据下沉、到期删除，是控制成本最有效的手段之一。

**一个常见坑**：把大量日志长期放在"热"层，成本会高得离谱；而把需要频繁读取的数据放进"归档"层，取回时又慢又贵。

## 第六章 分布式系统原理：CAP 与共识

### 6.1 CAP 定理

**CAP 定理**指出：分布式数据系统在**一致性（Consistency）**、**可用性（Availability）**、**分区容错性（Partition tolerance）** 三者中，无法同时完全满足。

| 属性 | 定义（Gilbert & Lynch 的表述） |
|------|-------------------------------|
| 一致性 C | 每个读操作都返回最近一次写的结果，或返回错误（即线性一致性） |
| 可用性 A | 每个发往非故障节点的请求都必须得到非错误响应 |
| 分区容错性 P | 系统在网络分区（消息丢失或延迟）时仍能继续运行 |

**它的来历**：Eric Brewer 于 2000 年在 ACM PODC 会议的主题演讲中提出这一猜想，因此也叫"布鲁尔定理"；2002 年，MIT 的 Seth Gilbert 与 Nancy Lynch 给出了严格证明。

> 来源：Brewer, E. A., "Towards Robust Distributed Systems", ACM PODC 2000 主题演讲；Gilbert, S. & Lynch, N., "Brewer's Conjecture and the Feasibility of Consistent, Available, Partition-Tolerant Web Services", *ACM SIGACT News*, 2002。

### 6.2 如何正确理解 CAP

**CAP 最大的误读是"三选二"**。更准确的表述是：

- 网络分区在分布式系统中**不可避免**，因此 P 不是可选项；
- **真正的取舍只发生在分区期间**：是牺牲一致性（继续服务，可能返回旧数据），还是牺牲可用性（拒绝服务，保证不出错）；
- 网络正常时，系统可以同时提供一致性与可用性。

| 类型 | 分区期间的行为 | 常见例子 |
|------|----------------|----------|
| CP | 少数派停止服务，保证不出错 | 强一致数据库、共识系统 |
| AP | 继续服务，接受可能读到旧值 | 最终一致的分布式数据库、DNS |

Brewer 本人在 2012 年的回顾文章 *CAP Twelve Years Later* 中，也明确表示"三选二"的简化说法具有误导性。

### 6.3 PACELC：CAP 的补充

CAP 只讨论"分区时"的取舍，却对"平时"的代价只字未提。**PACELC** 补上这一点：

> **P**artition 时在 **A** 与 **C** 间取舍；**E**lse（无分区时）在 **L**（延迟）与 **C**（一致性）间取舍。

**直觉**：即使网络正常，要保证强一致也需要节点间来回通信，这会带来延迟。所以"要不要强一致"在平时也是一个成本问题。

> 来源：Abadi, D., "Consistency Tradeoffs in Modern Distributed Database System Design", *IEEE Computer*, 2012（PACELC 于 2010 年提出）。

### 6.4 BASE：与 ACID 相对的一派

| 对比 | ACID | BASE |
|------|------|------|
| 主张 | 强一致、事务安全 | 基本可用、柔性状态、最终一致 |
| 适用 | 银行转账等强一致场景 | 社交动态、商品浏览等可容忍短暂不一致 |
| 代价 | 复杂、性能受限 | 需业务层处理中间态 |

**BASE** = **B**asically **A**vailable（基本可用）+ **S**oft state（软状态）+ **E**ventually consistent（最终一致）。

**关键提醒**：**"最终一致"不等于"随便一致"**。它必须能说明"多久之后一致"以及"不一致时业务能否承受"——否则就是给自己埋雷。

### 6.5 共识：让多台机器达成同一个结论

在允许节点故障与网络分区的前提下，让一群机器对某个值达成一致，这叫**共识（Consensus）**。

| 算法 | 特点 |
|------|------|
| Paxos | 共识算法的理论基石，但难以工程实现 |
| Raft | 以可理解性为设计目标，广泛用于工程实现 |
| ZAB | 用于 ZooKeeper 的原子广播协议 |

共识算法的典型应用：选主、配置管理、分布式锁、强一致复制日志。

**共识与 CAP 的关系**：共识系统通常属于 **CP**——分区时宁可停止服务，也不允许出现两个"主"同时接受写。

### 6.6 分布式系统的其它"必知陷阱"

| 陷阱 | 说明 |
|------|------|
| 网络不可靠 | 消息会丢、会延迟、会重复、会乱序 |
| 时钟不可靠 | 各机器时钟有偏差，不能直接用本地时间排序 |
| 部分失败 | 系统的一部分坏了，另一部分还在跑，状态难以判断 |
| 重试的副作用 | 超时重试可能造成重复操作（需幂等设计） |
| 脑裂 | 分区两侧各自认为自己是主，需要多数派机制避免 |

**"分布式系统的第一准则：不要分布"** ——这句行业玩笑的意思是，分布式带来的复杂度极高，能不分就不分。

## 第七章 分布式存储与分布式计算

### 7.1 核心口号：移动计算，而不是移动数据

处理 10 PB 数据时，把数据搬到计算节点上传输，可能要几天。因此大数据系统的第一原则是：

> **把程序送到数据所在的地方去，而不是把数据搬到程序这里来。**

这句话来自 Google 2003 年的 **GFS（Google File System）** 论文与 2004 年的 **MapReduce** 论文，是整个大数据技术栈的共同设计前提。

**生活类比**：要统计全国仓库的库存，你不会把所有货物运到一个地方数，而是**派统计员分头去各个仓库**，再把结果汇总。

### 7.2 分布式文件系统

| 概念 | 说明 |
|------|------|
| 大块存储 | 文件被切成很大的块（如 128MB 级），便于顺序读写 |
| 多副本 | 每块存多份，分散在不同机器/机架上 |
| 一次写入多次读取 | 面向批处理，简化一致性 |
| 廉价商用硬件 | 假设硬件会坏，靠软件容错 |
| 数据本地性 | 调度任务时优先分配到数据所在的机器 |

**HDFS（Hadoop Distributed File System）** 是 Google GFS 的开源对应实现：一个 NameNode 记录元数据，多个 DataNode 存数据块。

> 设计假设很重要：HDFS 适合"一次写入、多次读取"的大文件批处理，**不适合大量小文件**（元数据会压垮 NameNode），也不适合频繁随机写。

### 7.3 MapReduce：把并行变得简单

**MapReduce** 由 Google 的 Jeffrey Dean 与 Sanjay Ghemawat 在 2004 年提出，其论文题为 *MapReduce: Simplified Data Processing on Large Clusters*（发表于 OSDI 2004）。

它的核心是让使用者**只写两个函数**：

| 阶段 | 用户提供 | 作用 |
|------|----------|------|
| Map | 映射函数 | 把每条输入记录转成一个或多个 (键, 值) |
| Reduce | 归约函数 | 把相同键的所有值合并成一个结果 |

框架负责其余所有麻烦事：**数据切分、任务调度、并行执行、网络传输、故障重试**。

以"统计每个单词出现次数"为例：

```
输入：一堆文档
Map：每读到 "hello world"，输出 (hello,1) (world,1)
Shuffle：把相同键的中间结果汇集到一起
Reduce：把 (hello,[1,1,1]) 求和 → (hello, 3)
输出：每个单词的词频
```

**Shuffle 阶段是 MapReduce 的性能关键**，也是它相对较慢的主要原因——中间结果要大量写盘与网络传输。

### 7.4 Apache Hadoop

**Hadoop** 是 MapReduce 的开源实现。它起源于 Doug Cutting 与 Mike Cafarella 在 2002 年启动的 Apache Nutch 项目；Google 2003 年的 GFS 与 2004 年的 MapReduce 论文给了他们关键思路。2006 年 2 月，相关实现从 Nutch 中独立出来，成为 Apache 的 Hadoop 子项目，名字来自 Cutting 儿子的玩具大象。

| 组件 | 作用 |
|------|------|
| HDFS | 分布式存储 |
| MapReduce | 分布式批处理计算 |
| YARN | 资源调度与集群管理 |
| 生态组件 | Hive（SQL 化查询）、HBase（列式 NoSQL）、ZooKeeper（协调）等 |

> 来源：Dean, J. & Ghemawat, S., *MapReduce: Simplified Data Processing on Large Clusters*, OSDI 2004；Apache Hadoop 项目历史（2006 年从 Nutch 分离）。

**Hadoop 的局限**：MapReduce 每轮中间结果都要落盘，迭代式算法（如机器学习训练）与交互式查询代价极高。这正是 Spark 的切入口。

### 7.5 从批处理到流处理

| 处理模式 | 特点 | 延迟 | 典型框架 |
|----------|------|------|----------|
| 批处理（Batch） | 攒一批数据一起算 | 分钟到小时 | Hadoop MapReduce、Spark |
| 流处理（Streaming） | 数据一到就算 | 毫秒到秒 | Flink、Spark Streaming、Kafka Streams |
| 微批（Micro-batch） | 把流切成很小的批 | 秒级 | Spark Streaming、Structured Streaming |
| Lambda 架构 | 批处理保证准确 + 流处理保证实时，两套并行 | 兼顾 | 需维护两套逻辑 |
| Kappa 架构 | 只用流处理一条链路 | 简化 | 依赖流处理的成熟度 |

**Lambda 架构的痛点是"同一套业务逻辑要写两遍"**，两边实现不一致就会出现"实时看板和离线报表数字对不上"的经典问题。Kappa 架构正是为了解决这个重复。

## 第八章 大数据处理框架

### 8.1 Apache Spark

**Spark** 由 Matei Zaharia 于 2009 年在加州大学伯克利分校的 AMPLab 开始开发，2010 年开源，2014 年成为 Apache 顶级项目。

它的核心创新是 **RDD（Resilient Distributed Dataset，弹性分布式数据集）**：一种**内存中**的容错数据集抽象。相比 MapReduce 每轮落盘，Spark 能在内存中复用中间结果，对**迭代算法**与**交互式查询**有数量级的加速。

| 组件 | 用途 |
|------|------|
| Spark Core | 基础调度与 RDD |
| Spark SQL | 结构化数据与 SQL 查询 |
| Spark Streaming / Structured Streaming | 流处理 |
| MLlib | 机器学习库 |
| GraphX | 图计算 |

> 来源：Zaharia, M. 等，*Spark: Cluster Computing with Working Sets*（2010）；*Resilient Distributed Datasets: A Fault-Tolerant Abstraction for In-Memory Cluster Computing*（NSDI 2012 最佳论文）。Spark 于 2010 年开源、2014 年成为 Apache 顶级项目。

**RDD 的容错方式很巧妙**：不存数据副本，而是记录"这个数据集是怎么从源头算出来的"（血统 / lineage）。某个分区丢了，就按谱系重算那一个分区即可。

### 8.2 Apache Flink

**Flink** 是面向**真正的流处理**设计的引擎，把"流"视为一等公民，批处理是流处理的特例。

| 特性 | 说明 |
|------|------|
| 事件时间语义 | 按数据实际发生时间处理，而非到达时间——解决乱序问题 |
| 状态管理 | 内置有状态计算与状态后端 |
| 精确一次（exactly-once） | 通过检查点机制保证不重不漏 |
| 窗口 | 滚动、滑动、会话窗口等 |

**"事件时间 vs 处理时间"为什么重要？** 手机信号差时，日志可能延迟几十分钟才到达。若按"到达时间"统计，结果会错乱；按"事件时间"配合水位线机制，才能在乱序到达的前提下仍给出正确结果。

### 8.3 Apache Kafka：数据管道

**Kafka** 由 LinkedIn 团队开发（2010 年前后启动，2011 年开源），是一个**分布式发布-订阅消息系统**，常被形容为"分布式提交日志"。

| 概念 | 说明 |
|------|------|
| 主题（Topic） | 消息的分类通道 |
| 分区（Partition） | 主题的并行单元，可水平扩展 |
| 生产者/消费者 | 写入 / 读取 |
| 消费者组 | 多个消费者分摊一个主题的消费 |
| 保留策略 | 消息可保留一段时间，支持重放 |

**为什么 Kafka 在架构里如此中心？** 因为它是系统间的**解耦层**：生产者只管写，消费者只管读，双方互不知晓。它同时承担**削峰填谷**（突发流量先入队）与**数据总线**（一份数据供多方消费）两个角色。

### 8.4 数据集成与调度

| 类型 | 作用 | 代表 |
|------|------|------|
| 数据抽取/同步 | 把业务库数据搬到分析系统 | CDC（变更数据捕获）工具 |
| 工作流调度 | 按依赖关系编排任务 | Airflow、Dagster 等 |
| SQL 查询引擎 | 直接在数据湖上跑 SQL | Trino/Presto、Hive |
| 表格式 | 为数据湖加上"表"的语义 | Delta Lake、Apache Iceberg、Apache Hudi |

**CDC（Change Data Capture）** 的直觉：不去"每天全量拉一遍数据库"，而是**订阅数据库的变更日志**，只搬变化的部分。这大幅降低了源库压力与延迟。

## 第九章 数据仓库、数据湖与湖仓一体

### 9.1 三代演进

| 阶段 | 结构 | 特点 | 局限 |
|------|------|------|------|
| 数据仓库（Warehouse） | 写入时定义模式（Schema-on-Write） | 结构清晰、查询快、治理好 | 只能存结构化数据、扩展贵、上新需求慢 |
| 数据湖（Lake） | 读取时定义模式（Schema-on-Read） | 什么都能存、便宜、灵活 | 容易变成"数据沼泽"、缺治理、查询性能不稳 |
| 湖仓一体（Lakehouse） | 在数据湖上加表格式与事务能力 | 兼顾灵活与治理 | 相对较新，工具生态仍在成熟 |

> 说明：数据湖仓是近年的架构演进方向，具体产品与能力以各项目官方文档为准。Apache Iceberg、Delta Lake、Apache Hudi 是常见的开放表格式实现。

### 9.2 数据仓库的核心概念

| 概念 | 说明 |
|------|------|
| 维度建模 | 用"事实表 + 维度表"描述业务 |
| 星型模型 | 一个事实表连接多个维度表 |
| 雪花模型 | 维度表进一步规范化 |
| 缓慢变化维度（SCD） | 处理"客户地址变了"这类历史问题 |
| 分层 | ODS（贴源层）→ DWD（明细层）→ DWS（汇总层）→ ADS（应用层） |
| ETL / ELT | 抽取-转换-加载 / 抽取-加载-转换 |

**ETL 与 ELT 的差别在于"什么时候转换"**：ETL 在加载前转换（适合算力有限、需严格控制），ELT 先原样加载再用目标系统算力转换（适合云上算力便宜、需保留原始数据）。

### 9.3 "数据沼泽"是怎么形成的

数据湖最大的风险不是技术，而是**治理**：

| 症状 | 根因 |
|------|------|
| 找不到数据 | 没有元数据目录 |
| 不知道字段含义 | 没有数据字典 |
| 不知道数据是否可信 | 没有数据质量校验 |
| 不敢用 | 不知道谁有权限、是否含个人信息 |
| 存了一堆没人用 | 没有生命周期与成本约束 |

**一句话**：没有治理的数据湖，只是更贵的垃圾场。

### 9.4 湖仓一体解决什么

| 能力 | 数据湖缺 | 湖仓一体补上 |
|------|----------|--------------|
| 事务 | 并发写易冲突 | ACID 事务 |
| 模式演进 | 改结构很麻烦 | 支持演进 |
| 时间旅行 | 无法查历史版本 | 可查询快照 |
| 性能 | 依赖文件布局 | 索引与统计信息优化 |
| 更新删除 | 难 | 支持行级更新（满足合规删除要求） |

**合规上的价值**：个人信息保护法赋予个人删除权，若分析系统无法删除单个用户的数据，就会形成合规缺口（见《数据安全与隐私保护》第十章）。

## 第十章 数据治理与合规

### 10.1 大数据时代的合规挑战

数据量越大、汇聚越多，"重新识别"的风险越高。**单看一条字段不敏感，拼起来可能就能定位到具体的人**——这叫"数据聚合风险"。

| 挑战 | 说明 |
|------|------|
| 一数多用 | 为 A 目的收集的数据被用于 B 目的（违反目的限制） |
| 汇聚重识别 | 多源数据拼接后能识别个人 |
| 跨境流动 | 数据出境需满足安全评估、认证或标准合同等条件 |
| 最小必要 | 大数据"先存后想"的文化与最小必要原则冲突 |
| 删除权落地 | 分布式存储与多副本让"彻底删除"变得困难 |
| 训练数据合规 | 生成式 AI 的训练数据来源与处理需合规 |

### 10.2 落地手段

| 手段 | 作用 |
|------|------|
| 数据分类分级 | 按敏感程度施加不同保护（《网络数据安全管理条例》明确要求） |
| 数据目录与血缘 | 知道"有什么数据、从哪来、被谁用" |
| 权限与脱敏 | 最小权限 + 展示/使用脱敏 |
| 加密与令牌化 | 静态与传输加密，敏感字段用令牌替代 |
| 审计日志 | 记录谁在何时访问了什么 |
| 生命周期管理 | 到期删除、冷热分层 |
| 隐私增强技术 | 差分隐私、联邦学习、安全多方计算等 |

**差分隐私的直觉**：在统计结果里加入精心设计的噪声，使"某个人是否在数据集中"无法被推断出来，同时整体统计规律仍然可用。

### 10.3 法规要点回顾

| 法规 | 施行日期 | 与云/大数据的关系 |
|------|----------|-------------------|
| 网络安全法 | 2017-06-01 | 网络运营者的安全义务 |
| 数据安全法 | 2021-09-01 | 数据分类分级、重要数据保护、数据出境 |
| 个人信息保护法 | 2021-11-01 | 处理规则、个人权利、跨境提供 |
| 网络数据安全管理条例 | 2025-01-01 | 细化落地：处理 1000 万人以上个人信息需履行更严义务；向其他处理者提供或委托处理个人信息、重要数据的处理情况记录须至少保存 3 年 |

> 来源：上述法律法规正式文本（详见《数据安全与隐私保护》第十章）。云上部署不改变合规责任——**责任共担模型下，数据合规始终是使用方的责任。**

## 第十一章 边缘计算：把算力搬到数据产生的地方

### 11.1 为什么要离开中心

云数据中心通常远离用户。把数据全部传回中心再返回结果，会遇到三个问题：

| 问题 | 说明 |
|------|------|
| 延迟 | 物理距离带来往返时延，自动驾驶、工业控制无法接受 |
| 带宽 | 一路摄像头每天产生海量视频，全传回中心成本极高 |
| 连接稳定性 | 网络中断时业务不能停 |
| 数据合规 | 某些数据要求本地处理、不出园区 |

**边缘计算（Edge Computing）** 把计算与存储下沉到**靠近数据产生的位置**——设备侧、网关侧、园区机房、运营商的边缘节点。

### 11.2 云—边—端的分工

| 层次 | 位置 | 适合做什么 |
|------|------|------------|
| 端（Device） | 传感器、摄像头、手机、车机 | 采集、极低延迟的即时反应、预处理 |
| 边（Edge） | 网关、基站、园区机房 | 本地实时分析、汇聚、过滤后上传 |
| 云（Cloud） | 集中数据中心 | 大规模训练、全局调度、长期存储、跨域分析 |

**分工原则**：**实时性要求高、数据量大、隐私敏感的放在边；需要全局视野、算力密集的放在云。**

**生活类比**：小区门口的保安（边）能立刻判断"这人是不是本小区的"，不需要每次都打电话给总部（云）；但总部的安防系统（云）才能做跨小区的趋势分析。

### 11.3 典型场景

| 场景 | 为什么需要边缘 |
|------|----------------|
| 工业质检 | 毫秒级判定，产线不能停 |
| 自动驾驶 | 时延必须在毫秒级，且网络可能中断 |
| 智能安防 | 视频数据量太大，只上传"事件" |
| 零售门店 | 本地客流分析，仅上传汇总指标 |
| CDN | 内容就近缓存（见《互联网与网络协议》第六章） |
| 物联网 | 海量设备数据先本地聚合 |

### 11.4 边缘计算的代价

| 代价 | 说明 |
|------|------|
| 运维复杂 | 节点数量多、环境恶劣、难以物理接触 |
| 资源受限 | 算力、内存、电力、散热都有限 |
| 一致性难题 | 边与云之间数据同步、断网期间如何自治 |
| 安全边界扩大 | 每个边缘节点都是潜在入口 |
| 更新困难 | 需要可靠的远程部署与回滚机制 |

**关键设计问题**：**断网时边缘节点要能自治**。这要求它具备本地决策能力与"重连后追平状态"的机制。

### 11.5 5G 与边缘的关系

5G 的高带宽、低时延、海量连接特性（见《互联网与网络协议》第五章）让边缘计算在无线场景下更具可行性：把算力放在基站侧的边缘节点，可以让移动设备在几毫秒内获得响应。**两者是互补而非替代关系**。

## 第十二章 Serverless 与云原生实践

### 12.1 Serverless：连"服务器规格"都不用选了

**Serverless（无服务器计算）** 并不是真的没有服务器，而是**用户不再感知服务器**：

| 对比 | 传统云主机 | 容器编排 | Serverless（函数） |
|------|------------|----------|--------------------|
| 你要管什么 | 操作系统、运行时、应用 | 镜像、编排配置、应用 | 只需写函数 |
| 伸缩 | 手动或自动（较慢） | 自动（较快） | 自动（极快，可到零） |
| 计费 | 按实例时长 | 按节点/实例 | **按实际调用次数与执行时间** |
| 空闲成本 | 有（机器一直开着） | 有（最低副本） | 通常为零 |
| 启动延迟 | 低 | 低 | 存在冷启动 |
| 适合 | 长期稳定负载 | 微服务、中等波动 | 事件驱动、波峰波谷剧烈 |

**"冷启动"是什么？** 函数长时间没被调用后，运行环境会被回收；下次调用需要重新初始化，因此首次响应偏慢。这是 Serverless 最常被诟病的点。

### 12.2 事件驱动：Serverless 的思维方式

Serverless 天然与"事件"配合：

```
文件上传 → 触发图片压缩函数
订单创建 → 触发通知函数
定时器到点 → 触发对账函数
```

**它的好处是把"运维一套常驻服务"变成"为一件事写一段代码"**；代价是调试困难、状态管理受限、厂商绑定风险高。

### 12.3 云原生的实践清单

| 实践 | 说明 |
|------|------|
| 容器化 | 一致的运行环境，消除"在我机器上是好的" |
| 声明式配置 | 描述期望状态，而非执行步骤 |
| 微服务 | 按业务边界拆分，独立部署与扩展 |
| 服务网格 | 把流量治理、加密、可观测性下沉到基础设施层 |
| 不可变基础设施 | 不修改运行中的实例，要改就换新实例 |
| 持续交付 | 小步、频繁、可回滚的发布 |
| 可观测性 | 日志、指标、链路追踪三支柱 |
| 混沌工程 | 主动注入故障，验证系统韧性 |

**"不可变基础设施"的直觉**：与其登上一台机器手工改配置（改完就没人知道它和别的机器有什么不同），不如**把新配置打成新镜像、整体替换**。这样每台机器的状态都是可追溯、可复现的。

### 12.4 微服务的收益与代价

| 收益 | 代价 |
|------|------|
| 独立部署、独立扩展 | 分布式复杂度（网络、一致性） |
| 技术栈可异构 | 调试与链路追踪困难 |
| 故障隔离 | 运维与治理成本高 |
| 团队并行开发 | 需要成熟的 DevOps 能力 |

**警示**：微服务不是"更先进的分层"，而是**分布式系统**。如果团队没有相应的自动化与可观测性能力，微服务会把简单问题变成复杂问题。**先单体、后拆分**往往更稳妥。

## 第十三章 云成本与选型

### 13.1 云成本的构成

| 项目 | 说明 |
|------|------|
| 计算 | 实例规格 × 时长，或函数调用次数 |
| 存储 | 容量 × 时长 + 请求次数 + 取回流量 |
| 网络 | **跨区/出网流量常常是意外账单的主要来源** |
| 数据库与中间件 | 常是成本大头（授权、规格、备份） |
| 可观测性 | 日志存储量与查询量可能非常可观 |
| 支持服务 | 企业级支持费用 |

**"网络出流量"是新手最常踩的坑**：数据在云内部流转通常便宜，一旦流到公网就按量计费，量大了会非常吓人。

### 13.2 省钱的主要手段

| 手段 | 说明 |
|------|------|
| 合适的计费模式 | 按需、预留/包年、竞价实例各适合不同负载 |
| 自动伸缩 | 闲时缩容，避免为峰值长期付费 |
| 冷热分层 | 老数据下沉到低成本存储 |
| 规格优化 | 找出长期低负载的实例并降配 |
| 架构优化 | 减少跨区调用、减少不必要的日志 |
| 成本可观测 | 按团队/项目打标签，让成本可见 |
| 定期清理 | 僵尸资源（未挂载的磁盘、废弃的负载均衡） |

**核心原则**：**成本优化的前提是可观测**。如果连"钱花在哪个团队、哪个服务"都不知道，优化无从下手。

### 13.3 "上云一定更便宜"吗

不一定。上云的收益主要在**弹性、敏捷、免运维**，而非绝对价格。

| 场景 | 上云更划算 | 自建更划算 |
|------|------------|------------|
| 负载波动大 | ✓ | |
| 快速试错、需频繁变更 | ✓ | |
| 负载长期稳定且规模巨大 | | ✓（可能） |
| 有严格数据本地化要求 | 混合云 | ✓ |
| 团队缺少运维能力 | ✓ | |

**正确的问题不是"云还是自建"，而是"哪部分该用云、哪部分该自建"**——这正是混合云流行的原因。

### 13.4 选型检查清单

| 维度 | 要问的问题 |
|------|------------|
| 合规 | 数据能否出境？是否需本地存储？ |
| 可用性 | 是否需要多可用区/多区域容灾？ |
| 锁定风险 | 是否大量使用厂商专有接口？迁移成本多大？ |
| 生态 | 依赖的托管服务是否齐全？ |
| 成本 | 三年总成本（TCO）如何？ |
| 团队 | 团队是否熟悉该技术栈？ |
| 退出 | 如果要走，数据能否完整导出？ |

## 第十四章 常见误区与 FAQ

**Q1：云就是把机房租给别人，对吗？**
不完全是。云的关键在于**自助、弹性、计量**。只租机柜但需人工申请、按年付费的，按 NIST 定义并不构成云。

**Q2：云上数据一定不安全吗？**
风险方向不同。云厂商在物理安全、基础设施合规上通常强于中小自建机房；但**配置错误、权限过大、密钥泄露**是云上最常见的事故原因——这部分责任在用户。责任共担模型是理解这个问题的钥匙。

**Q3：虚拟机过时了吗？**
没有。容器共享内核，隔离强度弱于虚拟机；对多租户强隔离、需要自定义内核的场景，虚拟机仍是首选。**容器与虚拟机是互补关系**，容器本身也常运行在虚拟机里。

**Q4：Kubernetes 是必须的吗？**
不是。少量容器用简单编排甚至脚本就够。Kubernetes 的收益随规模与团队成熟度增长，**过早引入会带来显著的学习与运维负担**。

**Q5：CAP 是不是"三选二"？**
这个流行说法具有误导性。更准确的表述是：**P 不可避免，真正的取舍只在分区期间发生在 C 与 A 之间**；网络正常时两者可兼得。Brewer 本人也在 2012 年澄清过这一点。

**Q6：上了 Spark 就一定比 Hadoop 快吗？**
迭代与交互式场景通常快很多；但极简单的单趟批处理，Spark 的内存优势不明显，反而可能因资源占用更大而吃亏。**取决于工作负载形态**。

**Q7：数据湖能替代数据仓库吗？**
多数企业的现实答案是"两者都要"，并用湖仓一体架构减少割裂。纯数据湖容易退化为数据沼泽，纯数仓又难以容纳非结构化数据。

**Q8：Serverless 适合所有应用吗？**
不适合。长时任务、需要常驻连接（如 WebSocket 长连接）、对冷启动敏感的场景都不合适。它最适合**事件驱动、突发、短时**的任务。

**Q9：边缘计算会取代云吗？**
不会。边缘解决"近处实时"，云解决"全局规模"。主流模式是**云边端协同**：边做实时过滤与响应，云做训练与全局分析。

**Q10：大数据一定要用分布式吗？**
不是。若数据能装进一台机器的内存或磁盘，单机工具往往更快、更简单。**分布式的复杂度只有在单机确实撑不住时才值得付出。**

## 第十五章 一次请求在云上的完整旅程

把本篇的概念串起来，看一个用户在手机上点击"下单"之后，云上到底发生了什么。

```
① 用户点击
   ▼
② 域名解析（DNS）→ 拿到最近的接入点 IP（见《互联网与网络协议》）
   ▼
③ 边缘节点 / CDN
   静态资源（图片、脚本）就近返回；动态请求转发到后端
   ▼
④ 负载均衡
   按策略把请求分到某个可用区的实例；健康的实例才收流量
   ▼
⑤ 网关 / 服务网格
   鉴权、限流、路由；拒绝越权与异常流量
   ▼
⑥ 应用层（容器 / 函数）
   无状态服务横向扩展；有状态部分走持久化存储
   ▼
⑦ 缓存层
   命中则直接返回，极大降低数据库压力
   ▼
⑧ 数据库 / 分布式存储
   强一致数据走事务；多副本保证不丢
   ▼
⑨ 消息队列
   下单事件入队，通知、库存、风控等下游异步消费（削峰解耦）
   ▼
⑩ 分析链路
   CDC 抽取变更 → 数据湖/湖仓 → 报表与模型训练
   ▼
⑪ 可观测性
   日志、指标、链路追踪贯穿全流程；异常触发告警
   ▼
⑫ 计量与账单
   每一层的用量都被记录，按量计费
```

这张图里有几个值得记住的设计要点：

| 环节 | 对应原理 | 为什么这样设计 |
|------|----------|----------------|
| CDN / 边缘 | 边缘计算 | 减少延迟与回源带宽 |
| 负载均衡 + 多可用区 | 可用性设计 | 单点故障不影响服务 |
| 无状态应用 | 容器化前提 | 可随时替换、随意扩缩 |
| 缓存 | 空间换时间 | 保护数据库这一最贵资源 |
| 消息队列 | 解耦与削峰 | 上下游可独立伸缩、独立故障 |
| 多副本存储 | CAP 取舍 | 在一致性与可用性间按业务选择 |
| 事件入数据湖 | 数据链路 | 交易与分析分离，互不影响 |
| 计量 | NIST "可计量服务"特征 | 按用量计费的基础 |

**一个重要的观察**：这张图里几乎每一个环节，都可以在本板块的前几篇里找到对应的底层原理——域名解析与 TLS 在《互联网与网络协议》，缓存与内存层次在《计算机原理与组成》，分析链路里的算法与数据结构在《算法与数据结构》，鉴权与加密在《数据安全与隐私保护》。

**云不是另一套技术，而是把这些技术以服务的形式重新组织了一遍。**

## 小结

- **云计算**按 NIST **SP 800-145** 的定义由五特征（自助、泛在、池化、弹性、可计量）、三模型（IaaS/PaaS/SaaS）、四部署（公有/私有/社区/混合）组成；判定标准是**特征**，不是"是否用了虚拟机"。
- **责任共担模型**是云上安全与合规的第一原则：厂商负责"云的安全"，你负责"云里的安全"，数据与权限始终是你的责任。
- 云的两块技术地基是**虚拟化**（虚拟硬件，隔离强、较重）与**容器**（虚拟操作系统，轻量、启动快）。**OCI 规范**（2015）统一了镜像与运行时，**Kubernetes**（2014 年开源、2015 年捐赠 CNCF）成为编排事实标准。
- 分布式系统的核心取舍由 **CAP 定理**刻画（Brewer 2000；Gilbert & Lynch 2002 证明），**PACELC** 补上了"无分区时的延迟—一致性权衡"；**共识算法**（Paxos、Raft）是强一致系统的基石。
- 大数据的第一原则是**移动计算而非移动数据**，这一思想贯穿 **GFS（2003）与 MapReduce（2004）**、Hadoop（2006 年从 Nutch 分离）与 Spark（2009 年始于 UC Berkeley AMPLab，2014 年成为 Apache 顶级项目）。
- 数据架构经历了**数据仓库 → 数据湖 → 湖仓一体**的演进，核心张力是"结构化的效率"与"原始数据的灵活性"；没有治理的数据湖会退化为**数据沼泽**。
- 数据合规与云的结合点是**分类分级、最小必要、删除权落地与跨境规则**；《网络数据安全管理条例》（2025-01-01 施行）要求处理 1000 万人以上个人信息者履行更严义务。
- **边缘计算**解决延迟、带宽、连接与本地合规问题，与云形成**云边端协同**；**Serverless** 用"按调用计费"换来零空闲成本，代价是冷启动与厂商绑定。
- 成本优化的前提是**可观测**；上云不等于更便宜，正确的问题永远是"哪部分上云、哪部分自建"。

回到本板块的起点：从《计算机原理与组成》里一台机器的寄存器，到《互联网与网络协议》里的数据包，再到本篇成千上万台机器的协作——**计算机科学的主线，始终是把复杂问题切成足够小的部分，再用清晰的规则把它们重新连起来。**
