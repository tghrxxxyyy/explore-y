# 数据安全与隐私保护

> 子类：计算机与AI ｜ 难度：成人通识 ｜ 阅读时长：约 30 分钟

## 导语

你在电商下单时输入的那串银行卡号，在手机里存了几年的家庭照片，体检报告上那一行诊断结论——它们一旦离开你的设备，接下来去了哪里、被谁看过、会不会被卖掉？这不是杞人忧天：2017 年，美国征信机构 Equifax 因一个未及时修补的漏洞，让约 1.47 亿人的身份证号级的敏感信息暴露在外；2018 年，万豪旗下喜达屋的预订数据库被发现已被人潜伏多年。

数据安全与隐私保护，本质上是回答三个问题：**信息如何不被偷看？不被篡改？不被弄丢？** 本篇从密码学底座讲起——对称加密、非对称加密、哈希函数这三块基石；再向上搭起 PKI 证书体系与 HTTPS 这条"加密管道"；然后看待真实世界的泄露案例、权限控制、备份恢复，最后落到中国的《个人信息保护法》等法规要点。

技术事实均标注来源（如 `NIST FIPS 197`、`IETF RFC 8446`、`W3C`、《中华人民共和国个人信息保护法》条文序号），便于延伸查证。原理层面长期有效，产品与版本以写作时为准。

## 第一章 为什么需要数据安全：CIA 三元组

### 1.1 一句话定义

**信息安全**是"保护信息的保密性、完整性和可用性"的一整套技术与管理措施（ISO/IEC 27001 家族的核心概念）。它常被概括为 **CIA 三元组**：

| 属性 | 英文 | 含义 | 被破坏的例子 |
|------|------|------|--------------|
| 保密性 | Confidentiality | 只有被授权者能看 | 数据库被拖库、聊天记录被窃听 |
| 完整性 | Integrity | 数据不被擅自改动 | 转账金额被中间人改成别的数字 |
| 可用性 | Availability | 需要时能正常访问 | 勒索软件锁死文件、DDoS 打瘫网站 |

三者往往此消彼长。例如把系统锁得极严（保密性高）可能让正常用户也登不进去（可用性下降）——安全设计从来是权衡，而不是"全都拉满"。

### 1.2 再加两把尺子：真实性与不可否认

工程实践中，CIA 之外常补上两项：

- **真实性（Authenticity）**：确认"你确实是你说的那个人/那台机器"。
- **不可否认性（Non-repudiation）**：发送方事后不能抵赖"这条消息不是我发的"。

数字签名（见第三章）主要就是为了提供这两点。

### 1.3 威胁从哪里来

| 威胁类别 | 典型手法 | 一句话本质 |
|----------|----------|------------|
| 恶意软件 | 病毒、木马、勒索软件、挖矿程序 | 让程序替攻击者干活 |
| 社会工程 | 钓鱼邮件、冒充客服、假二维码 | 骗人自己交出凭证 |
| 网络攻击 | 中间人、DoS/DDoS、SQL 注入 | 从通道或输入口钻进去 |
| 内部风险 | 越权访问、离职带走数据、误操作 | 边界内的人也不该全信 |
| 供应链 | 第三方组件植入后门 | 信任链条上最弱的一环 |
| 物理与灾害 | 硬盘损坏、机房起火、断电 | 非人为的"可用性"事故 |

> 注：以上分类是业界通用视角，具体清单可参考 `NIST SP 800-53`（安全与隐私控制）与 `OWASP Top 10`（Web 应用风险）等。

### 1.4 安全是过程，不是产品

买一台防火墙不等于"安全了"。业界常说安全是一段**持续的过程**：识别资产 → 评估风险 → 部署控制 → 监控检测 → 响应恢复。缺乏任何一个环节，前面投入都可能被一次未修补的漏洞抹平——Equifax 的教训正是"补丁管理"这个最不起眼的环节。

## 第二章 密码学基石之一：对称加密

### 2.1 从凯撒密码说起

最早的加密思想极其朴素：把字母表整体挪几位。凯撒密码挪 3 位，`hello` 就变成 `khoor`。它的致命弱点是**密钥空间太小**——总共只有 25 种可能，暴力枚举一瞬间就破了。

一个加密方案的安全性，应当**只依赖于密钥的保密，而不依赖于算法的保密**。这个原则有一个专门名字，来自 19 世纪的密码学家奥古斯特·柯克霍夫，称为**柯克霍夫原则（Kerckhoffs's principle）**。现代密码算法全部公开，安全性全押在密钥上。

### 2.2 对称加密：一把钥匙开一把锁

**对称加密（Symmetric Encryption）**：加密和解密使用**同一把密钥**。

```
明文 ──[密钥 K 加密]──▶ 密文 ──[密钥 K 解密]──▶ 明文
```

优点是快——现代 CPU 普遍内置 AES 硬件指令，加解密吞吐量极高，适合加密大块数据。缺点也很直白：**通信双方得先共享那把密钥**，而"怎么安全地把密钥给对方"本身又是个难题（俗称"密钥分发问题"）。

### 2.3 分组密码与流密码

| 类型 | 工作方式 | 代表算法 | 典型场景 |
|------|----------|----------|----------|
| 分组密码 | 把数据切成固定大小的"块"（如 128 位）逐块加密 | AES、SM4、Camellia | 文件、磁盘、TLS 记录 |
| 流密码 | 生成与明文等长的密钥流，逐位/逐字节异或 | ChaCha20、RC4（已弃用） | 低延迟通信 |

### 2.4 AES：今天的对称加密标准

**AES（Advanced Encryption Standard，高级加密标准）** 由比利时密码学家 Joan Daemen 与 Vincent Rijmen 设计（原算法名 Rijndael），2001 年由美国国家标准与技术研究院（NIST）发布为 **FIPS 197**。

- 分组长度固定 **128 位**；
- 密钥长度可选 **128 / 192 / 256 位**；
- 名字里的"192/256"指密钥长度，不是分组长度——这是常见误解。

> 来源：NIST, *FIPS 197: Advanced Encryption Standard (AES)*, 2001。中国对应的商用分组密码标准是 **SM4**（GB/T 32907）。

### 2.5 工作模式：光有 AES 不够

分组密码只解决"怎么加密一个块"，实际数据长度任意，需要**工作模式**把块串起来：

| 模式 | 英文 | 特点 | 安全性提示 |
|------|------|------|------------|
| ECB | Electronic Codebook | 每块独立加密 | **不推荐**：相同明文块产生相同密文，会泄露结构 |
| CBC | Cipher Block Chaining | 前一块密文参与下一块 | 需要随机 IV；易受填充预言攻击 |
| CTR | Counter | 把块密码当流密码用 | 可用并行；**绝不能重复使用同一 nonce** |
| GCM | Galois/Counter Mode | CTR + 认证标签 | 同时提供加密与完整性，TLS 常用 |

> 来源：NIST, *SP 800-38A*（工作模式）、*SP 800-38D*（GCM/GMAC）。

ECB 的经典演示是加密一张分块色块图：整张图轮廓依然清晰可辨，因为相同颜色块加密结果相同。**对称加密必须配合合适的工作模式和随机初始向量（IV/nonce）**，否则等于把门锁好却把钥匙插在门上。

### 2.6 对称加密的软肋

1. **密钥分发**：N 个人两两通信需要 N(N-1)/2 把密钥，规模爆炸。非对称加密正是为解决它而生。
2. **密钥管理**：密钥存在哪、多久轮换、谁能取用，往往比算法本身更容易出事。
3. **没有"身份"**：对称加密只能保证"持有同一密钥的人"能解密，无法证明对方是谁（任何人都可能偷到密钥）。

## 第三章 密码学基石之二：非对称加密

### 3.1 公钥密码的革命

1976 年，Whitfield Diffie 与 Martin Hellman 发表了《密码学的新方向》，提出用**一对数学上相关的密钥**替代共享密钥：

- **公钥（Public Key）**：可以随便公开，别人用它加密给你；
- **私钥（Private Key）**：只有你持有，用它解密。

从公钥**在计算上无法反推**私钥，这是整座大厦的地基。这个思路被称为**公钥密码学（Public-Key Cryptography）**或非对称加密。

### 3.2 三种主流算法

| 算法 | 数学难题 | 标准出处 | 特点 |
|------|----------|----------|------|
| RSA | 大整数分解 | RFC 8017（PKCS #1 v2.2） | 最早普及，密钥长、运算慢 |
| ECC / ECDSA | 椭圆曲线离散对数 | FIPS 186-4 / 186-5、RFC 5639 | 同等安全强度下密钥更短 |
| Diffie-Hellman / ECDH | 离散对数 | RFC 7748（X25519）、NIST SP 800-56A | 专门用于协商密钥，不加密数据本身 |

> 来源：RSA 由 Ron Rivest、Adi Shamir、Leonard Adleman 于 1977 年提出，其密码学规范现收录于 IETF RFC 8017。数字签名标准见 NIST FIPS 186 系列（最新为 FIPS 186-5，2023 年）。

### 3.3 密钥长度对比：为什么 256 位就够了

不同算法的"安全强度"不能按位数直接比较，需换算成**等价安全位数**（大致对应暴力破解所需的工作量）：

| 对称加密 | RSA / DH | 椭圆曲线 ECC | 大致等价安全强度 |
|----------|----------|--------------|------------------|
| 80 位 | 1024 位 | 160 位 | 已不安全 |
| 112 位 | 2048 位 | 224 位 | 可接受下限 |
| 128 位 | 3072 位 | 256 位 | 当前主流目标 |
| 256 位 | 15360 位 | 512 位 | 长期高保证 |

> 这张换算表是 NIST *SP 800-57*（密钥管理建议）中的经典结论。它直观解释了为什么"RSA-2048 相当于 AES-112"——不是位数越大的算法越强，而是**数学难题的破解难度**决定了等效强度。

### 3.4 数字签名：用私钥"盖章"

非对称加密反过来用，就得到**数字签名**：

```
签名：用【私钥】对消息摘要加密（盖章）
验证：用【公钥】解密摘要并比对（验章）
```

它提供三项保证：

1. **真实性**：只有私钥持有者能签出这个签名；
2. **完整性**：消息被改动，摘要就对不上；
3. **不可否认性**：签名不可抵赖（前提是私钥没被别人拿到）。

注意：**签名不是加密**。签名不隐藏内容，只证明"谁发的、有没有被改"。

### 3.5 混合加密：HTTPS 的真实做法

非对称加密慢得出奇，直接用它传网页数据不可行。因此实际系统采用**混合加密（Hybrid Encryption）**：

```
① 用非对称加密（或密钥协商）安全地交换一个临时对称密钥
② 之后的全部数据用对称加密（如 AES-GCM）高速传输
```

> 这正是 HTTPS 的做法：TLS 握手阶段用 RSA/ECDHE 协商出会话密钥，随后用对称加密传输应用数据（RFC 8446，TLS 1.3）。

### 3.6 一个必须提前知道的事：量子计算

RSA 与 ECC 的安全性建立在"大整数分解"和"离散对数"很难算之上。而 Shor 算法证明，**足够强大的量子计算机能高效求解这两类问题**。为此 NIST 自 2016 年起推进**后量子密码（Post-Quantum Cryptography, PQC）**标准化，并已发布一系列新标准。

> 说明：PQC 标准入选算法与编号请以 NIST 官方发布为准，本篇不列举具体编号以免过时。当前实用系统仍以 RSA/ECC 为主，向 PQC 迁移属于中长期任务。

## 第四章 密码学基石之三：哈希函数

### 4.1 哈希是什么

**哈希函数（Hash Function）** 把任意长度的输入，压缩成固定长度的输出（摘要 / digest）：

```
"hello"  ──SHA-256──▶  2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
```

（上例为 SHA-256 对 `hello` 的标准结果，可自行验证。）

### 4.2 三个关键性质

| 性质 | 含义 | 为什么重要 |
|------|------|------------|
| 单向性（原像抗性） | 由摘要推不出原文 | 用于密码存储 |
| 抗第二原像 | 给定输入，找不到另一个不同输入得到相同摘要 | 防止伪造 |
| 抗碰撞 | 找不到任意两个不同输入产生同一摘要 | 数字签名、证书安全 |

### 4.3 SHA 家族：从 SHA-1 到 SHA-3

| 标准 | 输出长度 | 状态 | 出处 |
|------|----------|------|------|
| MD5 | 128 位 | **已不应用于安全用途** | RFC 1321 |
| SHA-1 | 160 位 | **已弃用**（碰撞已被实证） | FIPS 180-4 |
| SHA-256 / SHA-512 | 256 / 512 位 | 当前主流 | FIPS 180-4 |
| SHA3-256 / SHAKE | 可变 | 新一代海绵结构 | FIPS 202 |

> 来源：NIST, *FIPS 180-4: Secure Hash Standard*, 2015；*FIPS 202: SHA-3 Standard*, 2015。MD5 与 SHA-1 的安全退役建议见 RFC 6151（2011）。

**为什么 MD5/SHA-1 要退役？** 它们的"抗碰撞"已被实际攻破：攻击者可以构造两份内容不同、但摘要相同的文件。这意味着用 SHA-1 签名的证书、用 MD5 校验的下载包，都可能被掉包而校验"通过"。

### 4.4 HMAC：带密钥的哈希

单纯哈希无法防伪造——任何人都能改数据后重新算一遍摘要。**HMAC（Hash-based Message Authentication Code）** 用一把共享密钥参与计算，从而同时提供**完整性**与**真实性**：

```
HMAC(K, message) = H( (K ⊕ opad) ‖ H( (K ⊕ ipad) ‖ message ) )
```

> 来源：RFC 2104；美国标准见 NIST FIPS 198-1。HMAC 是现代网络协议（TLS、IPsec、JWT 签名等）的常见组件。

### 4.5 密码存储：为什么不能直接哈希

如果网站把用户密码的 SHA-256 直接存库，攻击者拖库后有两条捷径：

1. **彩虹表**：预先算好海量常见密码的摘要，一查即得；
2. **GPU 暴力破解**：SHA-256 极快，普通显卡每秒能试几十亿次。

正确做法是**加盐 + 慢哈希**：

| 方案 | 核心思想 | 标准出处 |
|------|----------|----------|
| 加盐（Salt） | 每个密码配一段随机串，使彩虹表失效 | 通用实践 |
| PBKDF2 | 迭代数万至数十万次，拖慢暴力破解 | RFC 8018 |
| bcrypt | 基于 Blowfish，带可调 cost 因子 | 实践广泛但非 KDF |
| Argon2 | 内存困难 + 抗 GPU/ASIC，现代首选 | RFC 9106 |

> 来源：IETF 与 OWASP 的密码存储建议均推荐 **Argon2id** 作为新系统首选，PBKDF2 仅在需要 FIPS 合规时使用；bcrypt 不再推荐用于新系统。参数需要随硬件进步定期调高。

**关键区分**：这里的"哈希"是**密码学哈希**，与数据结构里的"哈希表"（见《算法与数据结构》）完全是两回事——后者追求快，前者故意要慢。

### 4.6 摘要算法的日常用途

- **完整性校验**：下载文件后核对 SHA-256，确认没被篡改；
- **去重与索引**：内容寻址存储、Git 提交 ID；
- **区块链**：区块间用哈希串成链，改动一处则后续全部对不上；
- **数字签名与证书**：先对消息取摘要，再对摘要签名（因为非对称运算慢）。

## 第五章 PKI 与数字证书：信任如何被"批发"

### 5.1 一个绕不开的问题

你用公钥加密给"某银行"发消息。可你怎么确定拿到的这把公钥真的是银行的，而不是中间人偷偷塞给你的？如果连公钥都被掉包，后面加密再强也毫无意义。

解决办法是引入一个双方都信的**第三方**，由它来担保"这把公钥属于这家机构"。这一整套体系叫 **PKI（Public Key Infrastructure，公钥基础设施）**。

### 5.2 数字证书：公钥的"身份证"

**数字证书**就是 CA 用自己私钥签署的一份文件，内容大意是："我，某某 CA，证明这把公钥属于 example.com。"

X.509 证书的主要字段：

| 字段 | 含义 |
|------|------|
| 版本 / 序列号 | 证书版本（v3 为主）与唯一编号 |
| 签发者（Issuer） | 签发这张证书的 CA |
| 主体（Subject） | 证书归属者（域名、组织名） |
| 有效期 | Not Before / Not After |
| 公钥信息 | 公钥算法与公钥值 |
| 扩展项 | 用途限制、Subject Alternative Name（SAN）等 |
| 签名 | CA 用私钥对上述内容的签名 |

> 来源：RFC 5280，*Internet X.509 Public Key Infrastructure Certificate and CRL Profile*。现代浏览器主要依据扩展项中的 **SAN** 字段来匹配域名，不再依赖旧的 Common Name。

### 5.3 信任链：从根 CA 到你访问的网站

```
根 CA（自签名，预装在系统/浏览器中）
   │ 签发
   ▼
中间 CA（Intermediate CA）
   │ 签发
   ▼
服务器证书（example.com）
```

验证过程是**自下而上**的：浏览器拿到服务器证书，用中间 CA 的公钥验证其签名 → 再用根 CA 的公钥验证中间 CA 的签名 → 最终落到本地**受信任根证书列表**。任何一环断了，就弹"证书不受信任"。

### 5.4 证书的生命周期

| 阶段 | 做什么 | 相关标准/协议 |
|------|--------|---------------|
| 生成密钥 | 在服务器上生成密钥对，私钥不外传 | — |
| 提交申请 | 生成 CSR（证书签名请求） | PKCS #10（RFC 2986） |
| 域名/主体验证 | CA 核实申请人确实控制该域名 | CA/Browser Forum 基线要求 |
| 签发 | CA 用私钥签出证书 | X.509（RFC 5280） |
| 部署 | 装入服务器并配置 | — |
| 吊销 | 私钥泄露或不再需要时作废 | CRL、OCSP（RFC 6960） |
| 续期 | 到期前重新签发 | 自动化用 ACME（RFC 8555） |

**为什么证书有有效期？** 短有效期是一种"自动纠错"机制：即使某张证书被错误签发，最坏影响也被限制在有效期内。这也是为什么业界趋势是有效期越来越短、并用 **ACME 协议**（Let's Encrypt 推广的自动化协议，RFC 8555）实现免费自动续期。

### 5.5 证书的类型

| 类型 | 验证内容 | 常见用途 |
|------|----------|----------|
| DV（域名验证） | 只验证域名控制权 | 个人站点、免费证书 |
| OV（组织验证） | 额外核实组织真实存在 | 企业官网 |
| EV（扩展验证） | 更严格的组织与法律身份核验 | 金融、政务 |

> 说明：EV 证书过去会让浏览器地址栏显示绿色，但主流浏览器已陆续取消该视觉差异（来源：Mozilla、Google 等浏览器官方的 UI 变更公告）。如今**不能仅凭地址栏外观判断网站可信度**。

### 5.6 信任体系的脆弱面

根 CA 数量有限但权力极大：**任何一家根 CA 被攻破或误签发，都可能危及海量网站**。历史上出现过多起 CA 误签发/被入侵事件，直接导致该 CA 被浏览器厂商移除信任。由此催生的改进包括：

- **证书透明度（Certificate Transparency, CT）**：所有公开证书必须记入可审计的日志，任何人都能查"有没有人给我域名签了证书"；
- **HTTP 公钥固定（HPKP）**：曾被提出，但因配置不当风险高，已被主流浏览器弃用；
- **CAA 记录**：域名可声明"只有指定 CA 才可为我签发证书"。

## 第六章 HTTPS：一次加密连接里发生了什么

### 6.1 HTTPS 是什么

**HTTPS = HTTP over TLS**：在明文 HTTP 之下加一层 TLS（Transport Layer Security）加密通道。

| 项目 | HTTP | HTTPS |
|------|------|-------|
| 加密 | 无，明文传输 | 有（TLS） |
| 默认端口 | 80 | 443 |
| 身份验证 | 无 | 依赖服务器证书 |
| 防篡改 | 无 | 有（完整性校验） |

> 来源：RFC 2818（HTTP over TLS，2000）。TLS 1.3 见 RFC 8446（2018）；TLS 1.2 见 RFC 5246，正逐步退役。

### 6.2 TLS 1.3 握手：1 个往返建立安全通道

TLS 1.3 把握手精简到 1 个往返（1-RTT），并支持会话恢复时的 0-RTT：

```
客户端                              服务器
  │── ClientHello（支持的版本、密码套件、随机数）──▶│
  │                                                │ 选参数、算密钥
  │◀── ServerHello + 证书 + 签名 + Finished ───────│
  │ 验证证书 → 双方导出相同的会话密钥               │
  │── Finished ──────────────────────────────────▶ │
  │◀════════ 之后全部用对称加密传输 ═══════════════▶│
```

三个要点：

1. **前向安全（Forward Secrecy）**：TLS 1.3 强制使用临时密钥协商（ECDHE）。即使服务器长期私钥将来泄露，**也无法解密过去记录的通信内容**。
2. **精简算法**：删除了 RC4、DES/3DES、静态 RSA 密钥交换、MD5/SHA-1 等一系列被认为不安全的算法。
3. **加密范围扩大**：证书本身在 TLS 1.3 中也是加密传输的，进一步减少可窥探的信息。

### 6.3 证书校验失败意味着什么

| 浏览器提示 | 可能原因 |
|------------|----------|
| 证书已过期 | 服务器忘记续期 |
| 证书域名不匹配 | 证书上的 SAN 与访问域名不符 |
| 证书链不完整 | 服务器漏发中间证书 |
| 证书不受信任 | 自签名，或签发 CA 不在信任列表 |
| 证书已被吊销 | 私钥泄露，已主动作废 |

对普通用户而言，看到这类警告**不要随手点"继续访问"**，因为中间人攻击正是以这种形态出现的。

### 6.4 关于 HTTPS 的五个常见误解

1. **"HTTPS 说明这个网站是好人"** —— 错。HTTPS 只保证"你与这个域名之间的通道加密"，不保证域名背后的人不做坏事。钓鱼网站同样可以申请到合法证书。
2. **"HTTPS 说明网站内容真实"** —— 错。加密不等于内容可信。
3. **"上了 HTTPS 就安全了"** —— 错。它只覆盖传输环节；服务器被拖库、弱口令、SQL 注入照样出事。
4. **"小锁图标代表安全"** —— 需谨慎。小锁只表示传输加密；某些浏览器已弱化该图标。
5. **"内部网络不需要 HTTPS"** —— 错。内网同样存在嗅探与横向移动风险，零信任模型（见第八章）明确要求"无论网络位置，通信一律加密"。

### 6.5 超越 HTTPS：其它加密层

| 层面 | 技术 | 保护范围 |
|------|------|----------|
| 传输层 | TLS | 客户端 ↔ 服务器 |
| 网络层 | IPsec（IETF RFC 4301 系列） | 站点 ↔ 站点（VPN） |
| 应用层 | SSH、PGP/GPG、Signal 协议 | 远程登录、邮件、即时通信 |
| 存储层 | 全盘加密、数据库透明加密 | 静态数据（data at rest） |

> 提示：**传输中（in transit）**与**静态（at rest）**是两个必须分别考虑的状态，只做其中之一都会留下缺口。

## 第七章 隐私泄露：风险图景与真实案例

### 7.1 个人数据的黑产链条

一条完整的个人数据泄露产业链通常长这样：

```
入侵/内鬼 → 拖库 → 数据清洗与去重 → 按"数据质量"分层定价
   → 下游：精准诈骗、撞库盗号、垃圾营销、身份冒用、征信包装
```

不同数据在暗市的价值差别很大：能直接形成资金损失的（银行卡号+密码、身份证号）最贵；单纯的联系方式单价极低，但靠**量大**取胜。这也是"社工库"经久不衰的原因。

### 7.2 标志性泄露事件

| 时间 | 事件 | 规模 | 技术根因 | 后果 |
|------|------|------|----------|------|
| 2013—2014 | Yahoo | 全部约 30 亿账户 | 凭证被窃、加密方式薄弱 | 巨额和解、收购价受影响 |
| 2013 | Target | 约 4100 万张卡 + 超 6000 万联系信息 | 第三方供应商凭证被盗 | 和解与赔偿 |
| 2014 | eBay | 约 1.45 亿用户 | 少量员工凭证被攻破 | 强制改密、监管处罚 |
| 2017 | Equifax | 约 1.47 亿美国用户 | **未及时修补 Apache Struts 已知漏洞** | 约 7 亿美元级和解 |
| 2018 | Marriott（喜达屋） | 最多约 5 亿，后修正为约 3.83 亿 | 系统被潜伏多年、缺乏分段 | 监管罚款、客户流失 |
| 2018 | Facebook / Cambridge Analytica | 约 8700 万用户画像被第三方滥用 | **接口设计允许过度抓取** | 巨额罚款、声誉重创 |
| 2021 | Colonial Pipeline | 输油管道停运数日 | 单点口令+缺乏多因素认证 | 支付赎金、能源供应中断 |

> 来源：各公司官方公告、监管机构（如英国 ICO、美国 FTC）公开文件及主流媒体调查报道。具体数字各方披露口径略有差异，上表采用公开报道中的常见值。

### 7.3 泄露的技术根因统计视角

对照 **OWASP Top 10（2021 版）**，泄露事件的根因高度集中在这几类：

| OWASP 类别 | 中文 | 与泄露的关系 |
|------------|------|--------------|
| A01:2021 | 失效的访问控制 | 越权查看他人数据（最常见） |
| A02:2021 | 加密机制失效 | 明文存储密码、弱加密、密钥硬编码 |
| A03:2021 | 注入 | SQL 注入直接拖库 |
| A05:2021 | 安全配置错误 | 默认口令、云存储桶误设为公开 |
| A06:2021 | 过时/有漏洞的组件 | 未打补丁的框架（Equifax） |
| A07:2021 | 身份认证失效 | 无多因素认证、撞库得手 |

> 来源：OWASP Foundation, *OWASP Top 10 – 2021*，基于对数十万个应用的统计与行业调查。

可以看到：**大多数泄露不是"密码学被破解"，而是基本工程纪律没做好**。这是本篇反复强调"安全是过程"的原因。

### 7.4 个人层面的防护清单

| 措施 | 作用 | 优先级 |
|------|------|--------|
| 不同网站用不同密码（用密码管理器） | 阻断撞库连锁反应 | 极高 |
| 开启多因素认证（MFA） | 口令泄露也难登录 | 极高 |
| 及时更新系统与应用 | 堵住已知漏洞 | 高 |
| 警惕钓鱼链接与二维码 | 减少凭证主动交出 | 高 |
| 关闭不必要的授权/定位/通讯录权限 | 减少数据面 | 中 |
| 定期检查重要账号的登录设备 | 及早发现异常 | 中 |
| 对敏感文件本地加密备份 | 防勒索、防丢失 | 中 |
| 少在非必要场景提供真实身份证号 | 减少敏感数据暴露 | 中 |

> 提示：本篇**不构成任何安全产品推荐**。上述为通用最佳实践，具体方案因人而异。

## 第八章 权限与访问控制：谁能碰这份数据

### 8.1 先分清：认证 ≠ 授权

| 概念 | 英文 | 回答的问题 | 例子 |
|------|------|------------|------|
| 认证 | Authentication | 你是谁？ | 输入密码 + 短信验证码 |
| 授权 | Authorization | 你能做什么？ | 是否有权删除这条记录 |
| 审计 | Auditing | 你做过什么？ | 操作日志 |

三者顺序不能颠倒，也不能省略任何一环。很多越权漏洞的根源就是把"登录了"当成了"什么都能做"。

### 8.2 四类访问控制模型

| 模型 | 英文 | 控制依据 | 典型场景 |
|------|------|----------|----------|
| 自主访问控制 | DAC | 资源所有者自行授权 | 传统文件权限（Linux 的 rwx） |
| 强制访问控制 | MAC | 系统按安全标签强制判定 | 军用、涉密系统 |
| 基于角色的访问控制 | RBAC | 按角色授予权限 | 企业后台、ERP |
| 基于属性的访问控制 | ABAC | 按用户/资源/环境属性动态判定 | 云平台、零信任 |

### 8.3 最小权限原则

**最小权限原则（Principle of Least Privilege, PoLP）**：任何主体只应获得完成当前任务**所必需的最小权限，且仅在该任务所需的时间内**。

它对应两个实践：

- **权限最小化**：日常账号不给管理员权限；数据库账号不给 DROP 权限。
- **即时提权（Just-In-Time）**：需要高权限时临时申请、用完即收回，而不是长期持有。

这条原则的价值在勒索软件时代格外凸显：攻击者拿到一个低权限账号后，能否横向移动到核心数据库，往往取决于权限有没有被"顺手给大"。

### 8.4 身份凭证的演进

| 代际 | 方式 | 抗钓鱼能力 |
|------|------|------------|
| 第一代 | 纯密码 | 无 |
| 第二代 | 密码 + 短信/邮件验证码 | 弱（可被实时转发） |
| 第三代 | 密码 + TOTP/硬件令牌 | 中 |
| 第四代 | 抗钓鱼认证（Passkey / WebAuthn、FIDO2） | 强 |

**为什么短信验证码不够？** 攻击者可以用假基站或"客服话术"实时诱导用户把验证码报过来。这也是业界（包括 NIST）近年明确建议**逐步用抗钓鱼的多因素认证替代纯短信**的原因。

**Passkey / WebAuthn**（Web 认证标准，由 W3C 与 FIDO 联盟制定）把密钥对存放在设备安全芯片中，私钥永不出设备，服务端只存公钥——从根本上消除了"口令被钓鱼"的可能。

> 来源：W3C, *Web Authentication: An API for accessing Public Key Credentials*（WebAuthn 规范）；FIDO2 相关规范由 FIDO Alliance 维护。NIST 在 *SP 800-63B*（数字身份指南）中对认证器强度作了分级。

### 8.5 零信任：不再依赖"内网即安全"

传统的"城堡加护城河"模型假设：内网可信、外网不可信。但云服务、远程办公、BYOD 让"内网"边界彻底模糊。

**零信任（Zero Trust）** 的核心口号是"**永不信任，始终验证**"。美国 NIST 于 2020 年发布 **SP 800-207《零信任架构》**，给出七条原则，其中最关键的四条是：

1. 所有数据源与计算服务都视为"资源"，需要保护；
2. **无论网络位置，所有通信一律加密并认证**；
3. 对单个资源的访问**按每次会话单独授权**，不因上一次访问而继承信任；
4. 访问决策**基于动态策略**（身份、设备状态、行为、环境等）。

架构上，零信任把决策拆成两个逻辑组件：**策略引擎（PE）** 负责"判断能不能放行"，**策略执行点（PEP）** 负责"执行放行或拦截"，中间还有**策略管理器（PA）** 下发指令。

> 来源：NIST, *SP 800-207: Zero Trust Architecture*, 2020 年 8 月。

### 8.6 权限相关的常见漏洞

| 漏洞 | 表现 | 后果 |
|------|------|------|
| 水平越权 | 改一下 URL 里的 ID 就看到别人的订单 | 数据泄露 |
| 垂直越权 | 普通用户能调管理员接口 | 系统被接管 |
| 默认口令 | 设备/中间件出厂密码未改 | 直接失守 |
| 权限残留 | 离职/转岗后权限未回收 | 内部风险 |
| 接口无鉴权 | 只在前端隐藏按钮，后端不校验 | 越权调用 |

**唯一可靠的防线是"服务端必须每次都校验"**：前端的任何隐藏、置灰都只是体验，不是安全。

## 第九章 备份与恢复：最后一道防线

### 9.1 备份、归档、容灾是三个不同的事

| 概念 | 目的 | 恢复速度 | 保留期 |
|------|------|----------|--------|
| 备份（Backup） | 数据损坏/丢失后恢复 | 较快 | 中长期滚动 |
| 归档（Archive） | 长期留存以备查证 | 慢 | 很长 |
| 容灾（Disaster Recovery） | 整站/整机房级故障时接管业务 | 最快 | 持续同步 |

把三者混为一谈，是很多"以为有备份"却恢复失败的根源。

### 9.2 3-2-1 原则

**3-2-1 备份原则**由摄影师 Peter Krogh 提出，后被 IT 行业广泛采纳：

- **3** 份数据副本（1 份原始 + 2 份备份）；
- **2** 种不同的存储介质（避免同一类介质同时失效）；
- **1** 份存放在异地（抵御火灾、水灾、区域性事件）。

在此基础上，业界近年补充了 **3-2-1-1-0** 的强化版：再加 **1** 份离线/不可变副本，以及 **0** 错误（即**恢复演练必须通过、可验证**）。

### 9.3 备份的三种类型

| 类型 | 每次备份内容 | 优点 | 缺点 |
|------|--------------|------|------|
| 全量 | 全部数据 | 恢复最简单 | 慢、占空间 |
| 增量 | 自上次**任意**备份后变化的部分 | 快、省空间 | 恢复要串起整条链 |
| 差异 | 自上次**全量**备份后变化的部分 | 恢复较快 | 空间介于两者之间 |

常见策略是"每周全量 + 每日增量/差异"，并定期做"合成全量"以减少恢复链长度。

### 9.4 RAID 不是备份

RAID（独立磁盘冗余阵列）通过多块磁盘镜像或校验来**提高可用性**，但它**不能替代备份**：

| 场景 | RAID 能否救 |
|------|-------------|
| 单块磁盘物理损坏 | 能（镜像/校验重建） |
| 误删文件 | **不能**（删除会同步到所有盘） |
| 勒索软件加密 | **不能**（加密同样同步） |
| 机房火灾 | **不能**（全在同一处） |

一句话：RAID 防"硬件坏"，备份防"数据坏/人出错/被攻击"。

### 9.5 两个必须量化的指标

| 指标 | 全称 | 回答的问题 |
|------|------|------------|
| RPO | Recovery Point Objective | 最多能容忍丢多少**时间**的数据 |
| RTO | Recovery Time Objective | 最多能容忍业务中断**多久** |

例：RPO = 15 分钟意味着备份/同步间隔必须 ≤ 15 分钟；RTO = 1 小时意味着恢复流程必须能在 1 小时内完成。**先定指标，再选方案**，否则容易花大钱买错东西。

### 9.6 勒索软件时代的备份要点

1. **不可变备份（Immutable）**：写入后在一定期限内无法修改或删除，攻击者即使拿到管理员权限也删不掉；
2. **离线副本**：物理隔离的介质/磁带，或拔网的存储；
3. **备份账号与生产账号分离**：避免域管理员一锅端；
4. **加密备份**：防止备份介质本身泄露；
5. **恢复演练**：最容易被忽略、也最致命的一环——没演练过的备份等于没有备份。

### 9.7 一个可落地的个人备份清单

- 手机照片：开启云同步 + 定期导出到本地硬盘；
- 重要文档：本地一份 + 加密后云盘一份；
- 密码：使用密码管理器，并导出加密备份（离线保存）；
- 每半年做一次"恢复测试"：真的从备份里还原一个文件出来。

## 第十章 法律与合规：《个人信息保护法》要点

### 10.1 中国的数据与网络安全法律体系

| 法律/法规 | 施行日期 | 定位 |
|-----------|----------|------|
| 中华人民共和国网络安全法 | 2017 年 6 月 1 日 | 网络空间安全管理的基础性法律 |

| 中华人民共和国个人信息保护法 | 2021 年 11 月 1 日 | 个人信息权益保护的专门法律 |
| 网络数据安全管理条例 | 2025 年 1 月 1 日 | 上述三法的配套行政法规，细化落地规则 |

> 来源：全国人民代表大会常务委员会、国务院公布的正式文本。网络安全法由十二届全国人大常委会第二十四次会议于 2016 年 11 月 7 日通过；数据安全法于 2021 年 6 月 10 日通过；个人信息保护法于 2021 年 8 月 20 日通过；《网络数据安全管理条例》以国务院令第 790 号公布，2024 年 8 月 30 日国务院常务会议通过、2024 年 9 月 24 日签署、2025 年 1 月 1 日起施行。

### 10.2 个人信息保护法的五项基本原则

《个人信息保护法》第五条、第六条明确：处理个人信息应当遵循 **合法、正当、必要和诚信** 原则，并且：

- 具有**明确、合理的目的**，与处理目的直接相关；
- 采取对个人权益**影响最小**的方式；
- 收集应限于实现处理目的的**最小范围**，不得过度收集。

> 来源：《中华人民共和国个人信息保护法》第五条、第六条。这四项原则（合法、正当、必要、诚信）被认为是全法的内容主线。

### 10.3 告知—同意：不是"点一下就行"

| 规则 | 依据 | 说明 |
|------|------|------|
| 处理前应告知 | 第十七条 | 告知处理者名称、目的、方式、种类、保存期限、权利行使方式等 |
| 同意须自愿、明确 | 第十四条 | 须在充分知情前提下自愿、明确作出 |
| 目的变更需重新同意 | 第十四条 | 目的、方式、种类变化须重新取得同意 |
| 可撤回同意 | 第十五条 | 处理者须提供便捷撤回方式 |
| 不得因拒绝而拒绝服务 | 第十六条 | 除非属于提供服务所必需 |
| 敏感信息需单独同意 | 第二十九条 | 生物识别、医疗健康、金融账户、行踪轨迹等 |
| 不满十四周岁需监护人同意 | 第三十一条 | 且须制定专门处理规则 |

### 10.4 个人信息定义与"敏感个人信息"

《个人信息保护法》第四条：个人信息是"**以电子或者其他方式记录的与已识别或者可识别的自然人有关的各种信息，不包括匿名化处理后的信息**"。

第二十八条列举的**敏感个人信息**包括：

- 生物识别信息
- 宗教信仰
- 特定身份
- 医疗健康
- 金融账户
- 行踪轨迹
- **不满十四周岁未成年人的个人信息**

敏感信息只有在"**具有特定的目的和充分的必要性，并采取严格保护措施**"的情形下才可处理。

**注意"匿名化"与"去标识化"的区别**：

| 概念 | 含义 | 是否仍属个人信息 |
|------|------|------------------|
| 去标识化 | 移除直接标识符，但借助额外信息仍可能重新识别 | **是** |
| 匿名化 | 无法识别特定自然人且不能复原 | **否** |

### 10.5 个人的七项权利

| 权利 | 条文 | 内容 |
|------|------|------|
| 知情权、决定权 | 第四十四条 | 有权限制或拒绝他人处理自己的个人信息 |
| 查阅、复制权 | 第四十五条 | 处理者应及时提供 |
| 可携带权 | 第四十五条 | 符合条件时可请求转移至指定处理者 |
| 更正、补充权 | 第四十六条 | 发现不准确、不完整可请求更正 |
| 删除权 | 第四十七条 | 目的已实现、撤回同意、停止服务等情形 |
| 解释说明权 | 第四十八条 | 有权要求解释处理规则 |
| 死者近亲属权利 | 第四十九条 | 为自身合法正当利益可行使查阅等权利 |

### 10.6 跨境提供个人信息的三条路径

第三十八条给出了向境外提供个人信息的条件（满足其一）：

1. 通过国家网信部门组织的**安全评估**；
2. 经专业机构进行**个人信息保护认证**；
3. 与国家网信部门制定的**标准合同**与境外接收方订立合同；
4. 法律、行政法规或国家网信部门规定的其他条件。

此外第三十九条规定，跨境提供还须**取得个人的单独同意**；第四十条要求关键信息基础设施运营者与达到规定数量的处理者，**将在境内收集和产生的个人信息存储在境内**。

> 补充：《网络数据安全管理条例》（2025 年 1 月 1 日施行）进一步细化了数据出境的安全评估、认证与标准合同路径，并规定未被相关部门告知或公开发布为重要数据的，不需要作为重要数据申报数据出境安全评估。

### 10.9 等级保护 2.0

中国还有一套面向**系统**而非个人的强制性安全基线——**网络安全等级保护制度**。其基本要求国家标准为 **GB/T 22239-2019**（俗称"等保 2.0"），把系统按受侵害后的危害程度分为五级，逐级给出技术与管理要求。《网络数据安全管理条例》第九条也明确要求"在网络安全等级保护的基础上，加强网络数据安全防护"。

> 来源：GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》。

## 第十一章 常见误区与 FAQ

**Q1：加密了就安全了吗？**
不。加密只解决"看不到"，还有密钥管理、端点被控、权限过大等问题。加密是必要非充分条件。

**Q2：把文件放进"回收站"算删除了吗？**
不算。文件内容仍在磁盘上，可被恢复工具找回。真正敏感的数据应使用安全擦除或全盘加密后丢弃密钥。

**Q3：用公共 Wi-Fi 一定危险吗？**
不一定"一定危险"，但风险明显更高（可被嗅探、可被伪造热点）。若必须使用，请确保访问的是 HTTPS 站点，并避免登录敏感账号；更稳妥的做法是使用可信的加密通道（如 VPN 或运营商流量）。

**Q4：HTTPS 网站能拿到我的明文密码吗？**
服务器端当然能拿到你提交的密码（它要校验），但**网络中的第三方看不到**。所以关键还是看这个网站是否值得信任。

**Q5：密码强度该追求"复杂"还是"长"？**
长度更重要。"Tr0ub4dor&3" 这类复杂短密码反而不如由多个随机词组成的长口令。同时**绝不复用**密码。

**Q6：匿名化之后就不算个人信息了吗？**
是的，按《个人信息保护法》第四条，匿名化处理后的信息不属于个人信息。但"去标识化"的数据仍受该法约束。

**Q7：备份不就是多存一份吗？**
不是。多存一份但从不演练恢复、从不做异地/离线副本，面对勒索软件与区域性灾难时可能全部失效。

**Q8：公司内网数据就不用加密传输了吧？**
应加密。零信任模型明确要求"无论网络位置，通信一律加密"，内网同样存在嗅探与横向移动风险。

## 第十二章 纵深防御：把安全当成系统工程

### 12.1 为什么单点防御必然失效

任何一项防护都有被绕过的可能：防火墙会被配置错误打开缺口，杀毒会被免杀，WAF 会被绕过，员工会被骗。因此成熟的安全体系遵循**纵深防御（Defense in Depth）**——在多个层面叠加独立控制，让攻击者即使突破一层，仍要面对下一层。

```
外部攻击者
   │  ① 边界防护（防火墙、WAF、DDoS 清洗）
   │  ② 身份与访问控制（MFA、最小权限、零信任）
   │  ③ 端点防护（EDR、补丁、磁盘加密）
   │  ④ 应用安全（输入校验、参数化查询、安全设计）
   │  ⑤ 数据安全（加密、脱敏、访问审计）
   │  ⑥ 检测与响应（日志、SIEM、应急预案）
   ▼  ⑦ 备份与恢复（离线/不可变副本）
```

这条链的强度取决于**最弱的一环**，而"人的环节"往往最弱。

### 12.2 安全左移

**安全左移（Shift Left）** 指把安全活动提前到开发早期，而不是等上线前才做渗透测试。理由是修复成本随阶段推进急剧上升——在需求设计阶段改一个逻辑漏洞，远比上线后被入侵再补救便宜。

| 阶段 | 可嵌入的安全活动 |
|------|------------------|
| 需求/设计 | 威胁建模、确定数据分类分级、明确合规要求 |
| 编码 | 安全编码规范、静态扫描（SAST）、依赖成分分析（SCA） |
| 构建 | 制品签名、镜像扫描、密钥不入库 |
| 测试 | 动态扫描（DAST）、交互式扫描（IAST）、渗透测试 |
| 运行 | 运行时防护（RASP）、日志监控、告警与响应 |
| 退役 | 数据安全销毁、权限回收 |

### 12.3 密码学实践中的常见错误清单

| 错误 | 为什么致命 | 正确做法 |
|------|------------|----------|
| 自创加密算法 | 未经公开检验，几乎必有结构性缺陷 | 用标准算法（AES、SHA-2/3、TLS） |
| 硬编码密钥 | 代码/镜像泄露即全盘失守 | 用密钥管理服务，密钥与代码分离 |
| 复用 IV/nonce | CTR/GCM 下复用会直接泄露明文异或 | 每次加密用唯一随机 nonce |
| 使用 ECB 模式 | 相同明文块产生相同密文，泄露结构 | 改用 GCM 等认证加密模式 |
| 用 MD5/SHA-1 做签名 | 抗碰撞已破，可被伪造 | 用 SHA-256 及以上 |
| 混淆"编码"与"加密" | Base64 不是加密，谁都能解 | 明确区分编码/摘要/加密 |
| 加密但无完整性校验 | 密文可被篡改且不被发现 | 用带认证的加密（AEAD） |
| 错误信息泄露细节 | 报错里带 SQL、路径、堆栈 | 统一友好报错，细节只入内部日志 |

> 提示：以上属于工程实践共识，具体实现请以所用语言/框架的官方安全指南与 OWASP 相关备忘单为准。

### 12.4 日志与审计：看得见才能管得住

| 原则 | 说明 |
|------|------|
| 记什么 | 认证成功/失败、权限变更、敏感数据访问、配置改动 |
| 不记什么 | 明文口令、完整卡号、私钥、会话令牌 |
| 保护日志 | 日志本身须防篡改（追加写、集中收集、访问受限） |
| 保留多久 | 依据合规要求与业务需要，通常不少于法定期限 |
| 如何使用 | 异常检测、事件溯源、合规审计 |

《网络数据安全管理条例》要求，向其他处理者提供或委托处理个人信息、重要数据的，**处理情况记录应当至少保存 3 年**（第十二条）。

### 12.5 事件响应的六个阶段

业界通用的事件响应流程（NIST SP 800-61 提出的生命周期）：

```
① 准备 → ② 检测与分析 → ③ 遏制 → ④ 根除 → ⑤ 恢复 → ⑥ 事后复盘
```

对应到中国的合规义务：

- 发生网络数据安全事件，应**立即启动预案**、防止危害扩大、按规定向主管部门报告（《网络数据安全管理条例》第十一条）；
- 事件对个人、组织合法权益造成危害的，应以电话、短信、即时通信工具、电子邮件或公告等方式**通知利害关系人**；
- 发现涉嫌违法犯罪线索的，应按规定向公安机关、国家安全机关报案。

**"报告"与"通知"是两件事**：前者对监管，后者对受影响的个人，都不能省。

### 12.6 一张给普通人的"安全生命周期"检查表

| 场景 | 该做什么 |
|------|----------|
| 新设备开箱 | 立即改默认口令、开启磁盘加密、开启自动更新 |
| 注册新账号 | 用密码管理器生成唯一密码、能开 MFA 就开 |
| 收到链接/二维码 | 先看域名，再决定点不点 |
| 安装 App | 只从官方渠道，检查权限是否合理 |
| 处理旧设备 | 退出账号、加密后安全擦除 |
| 每季度 | 检查重要账号登录设备、检查授权列表 |
| 每半年 | 做一次备份恢复演练 |

## 第十三章 五条值得记住的直觉

1. **加密解决的问题是"通道"与"静态"，不是"人"。** 一个拥有合法权限的内鬼，再怎么加密数据他都能看。
2. **密码学的强度由最弱一环决定。** AES-256 配一把 `123456` 的密钥，整体强度就是 `123456`。
3. **"能解密"和"能证明是谁"是两件事。** 前者靠对称加密，后者靠数字签名，二者不可互相替代。
4. **可用的敌人是复杂性。** 配置项越多、权限越乱、系统越老，出事的概率越高。简单可控比功能丰富更重要。
5. **备份的敌人是"以为有备份"。** 没演练过的备份、和生产同账号的备份、只有一份在线副本的备份，都约等于没有。

一张对照表总结"技术手段 ↔ 解决的问题"：

| 技术手段 | 解决的核心问题 | 不解决的问题 |
|----------|----------------|--------------|
| 对称加密 | 大数据的保密性 | 身份、密钥分发 |
| 非对称加密 | 密钥分发、身份、不可否认 | 大数据量加密（太慢） |
| 哈希函数 | 完整性、单向存储 | 保密性（摘要不含信息但原文可能被猜） |
| HMAC | 完整性 + 真实性（共享密钥） | 不可否认（双方都能生成） |
| 数字签名 | 真实性 + 完整性 + 不可否认 | 保密性 |
| TLS/HTTPS | 传输通道的机密与完整 | 服务器内部安全、内容可信度 |
| 访问控制 | 谁能在什么条件下做什么 | 数据本身被窃取后的保护 |
| 备份 | 可用性与可恢复性 | 保密性（需配合加密） |

## 小结

- 信息安全的底座是 **CIA 三元组**（保密性、完整性、可用性），再补上真实性与不可否认性；安全是**持续过程**，不是一次性采购。
- **对称加密**（AES，FIPS 197）快，但难解决密钥分发；**非对称加密**（RSA、ECC）解决分发与身份问题，但慢——因此实际系统普遍采用**混合加密**。
- **哈希函数**（SHA-2 / SHA-3）提供单向性与抗碰撞；密码存储必须**加盐 + 慢哈希**（Argon2id 为首选，RFC 9106）。
- **PKI 与 X.509 证书**（RFC 5280）把"信任"批发给少数 CA，再由**HTTPS（HTTP over TLS，RFC 8446）**把这份信任变成一条加密管道。
- 现实中的泄露，绝大多数败在**基础工程纪律**（未打补丁、配置错误、弱口令、越权），而非密码被数学破解——OWASP Top 10 是最好的自查清单。
- 权限控制的核心是**认证、授权、审计**三者分离，以及**最小权限原则**与**零信任（NIST SP 800-207）**。
- 面对勒索软件与灾难，**3-2-1（+1+0）备份原则**与**恢复演练**是最后的兜底。
- 合规层面，《个人信息保护法》（2021 年 11 月 1 日施行）确立了**合法、正当、必要、诚信**原则与个人七项权利，《网络数据安全管理条例》（2025 年 1 月 1 日施行）把规则进一步落到操作细节。
